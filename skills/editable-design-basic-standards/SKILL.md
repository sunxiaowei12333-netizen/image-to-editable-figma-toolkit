# 规范设计稿

## 默认直接编辑链接目标

用户提供的链接就是本轮编辑目标，三个阶段及所有跳步路径均默认 `editMode="in-place"`。取消整页/整稿复制前置，不另建交付 Page，不要求用户再次同意原位编辑；用户提供已有副本时直接编辑该链接，也不再复制。

操作前保存实际属性、根边界和截图，写入后独立回读并比较。只改已授权阶段和 `processingRootIds` 内的内容；范围外节点、共享母组件、发布样式/变量及组件库源文件保持只读。已有本地母组件仅在影响完全处于授权范围内时可改，不能因原位编辑扩大影响范围。

只有用户明确要求“复制一份/保留原稿再改”时，才用 `editMode="safe-copy"` 创建或复用独立目标：复制前记录源根/父级/顺序，复制后核验映射、尺寸、裁切、位置和基线一致，再只写副本并验证源稿未改。该例外不构成默认前置。为代表验证、组件派生或回退所需的最小临时样本可保留，但不自动扩成整页复制，验证后清理并审计。

## 默认字体与轻微字形差异

默认沿用设计稿在 Figma 中的实际字体 family/style、字重与有效文字样式，使用当前 Figma 工具可访问的字体；不从执行电脑猜选字体，不要求同事先核对或安装同一个本机字体版本。Figma MCP 在服务端运行，本机字体可见不代表 MCP 可用；缺少字体时先核对 Figma 已上传/共享字体，仅隔离依赖候选，不把本机字体版本排查当成全局前置。

普通 UI 文字的轻微边缘/字形渲染差异按 [字体与视觉容差](references/font-visual-policy.md) 自动验收、记录并继续，不逐项向用户确认。文案、实际字体与字重、字号、样式/Paint、位置、尺寸、换行、裁切、重叠和组件行为仍须正常；特殊字体或用户要求字形严格保持的文字不套用普通 UI 容差。明显影响排版、内容或视觉的差异只修复或回退对应族；写入范围保护或回退失败才停止整个任务。

本规则优先于下文和旧参考中的“任何非零像素即失败”“无临时阈值即停止”及“边缘波动必须逐项确认”。授权范围外内容和共享资产不得误改；仅在用户要求副本时，额外验证源稿未改及普通复制基线一致。

只执行第三阶段时，先读 [第三阶段确定执行路径](references/third-stage-execution.md)。使用 schemaVersion=2 的实际文件审计，并设 visualPolicy="text-edge-v1"；不能由执行模型临时修改固定容差。

本 Skill 延续 A-r2 的修复与保护规则。遇到字体或视觉探针失败时，先按 [诊断与修复](references/diagnosis-and-repair.md) 查明原因并复测，再按运行边界决定推进；首次错误不是跳过依据。

原生编辑器作为字体修复路径时，执行诊断参考中的“原生文字编辑的定位与提交”：以节点 ID 确认单一编辑目标，分步确认文字编辑焦点，逐次回读文案与受保护属性，并核对页顶层新增节点。连接或独立回读尚未恢复时，不把 UI 操作视为已保存的修复。

本 Skill 的运行模式、特殊字体保护和局部受限路由见 [运行与验收边界](references/run-contract.md)，优先于本文旧的全局阶段入口限制；质量通过标准不降低。

把已经可编辑的 Figma 节点分三阶段整理。默认直接编辑用户链接指定的节点/页面，不自动创建安全副本或新 Page。保留目标根 ID、既有父级、位置和画面边界，不额外包裹 Frame 或 Section。只有第三阶段实际抽取出的 Component/Component Set 可以放入独立的组件整理/预览 Section。普通规范联动、组件抽取和无损结构整理保持视觉不变；已确认的字体、文字重叠和间距缺陷按限定范围修复。

宋体/中文衬线文字必须使用思源宋体，保留原字重，不得降级为 PingFang。各阶段的通用缺失字体降级规则都不得覆盖此要求；字体名称与可用字重按[宋体必须使用思源宋体](references/typography-layout-repair.md#宋体必须使用思源宋体)核验。此规则按字体类别适用，不把黑体或无衬线标题改成宋体。

## 默认处理边界：只处理实际页面的当前可见内容

除非用户明确要求包含页面外内容，本 Skill 的读取、写入、问题统计和验收范围只包含实际界面画面根节点内当前可见内容及影响它的最小依赖。用户链接指向单个 Frame/Component 等界面根节点时，只处理该节点当前可见范围；链接指向同时摆放多张界面和外围说明的 Figma Page 时，先识别每张实际界面画面根节点并记录为 `processingRootIds`。

- 页面旁边、且不属于实际界面画面根节点后代的既有标注与上下文节点默认排除，例如字体/字号说明、尺寸或比例标注、适配说明、开发备注、箭头/连线、页外标题/序号和示意样例。它们原位保留，不得修改，也不进入字体缺失、文字/颜色 Style 覆盖矩阵、例外/未映射数量、组件候选、命名/结构清理或 P0 完成门槛。
- 写入前同时记录排除的顶层或独立节点为 `excludedContextNodeIds`，并在交付中说明排除数量和代表性类型。不能仅凭图层名称判断；以节点是否属于实际界面画面边界、是否参与产品页面内容为准。无法可靠判断的页外节点保持不动并列入排除清单，不为清零统计而处理。
- 页面画面内部真实展示给用户的标题、说明和装饰文字仍属于处理范围；第三阶段新建的组件整理/预览 Section 及其中必要标注仍按第三阶段既有规则审计。用户若明确要求处理某类外围标注或给出更窄范围，以用户指定范围为准。

默认执行 [当前可见范围](references/visible-scope.md)：先跳过隐藏及完全裁剪外的子树，再读取详细属性；这些内容原样保留，不进入处理或验收分母。保留影响可见结果的布局、裁剪、背景和组件依赖。下文与其他参考中的“全量”“全部子树”“完整回读”均受此范围约束；不因最终审计重新展开隐藏内容。用户明确要求其他状态或完整内容时才扩展。新审计记录 `scope`，可见画面、可编辑性、母组件同步与根边界仍按原门槛检查。

## 默认保留无等价排版例外

目标发布库经过限定 library key 的真实搜索与完整排版属性比较后，确认没有严格等价 Text Style 时，默认保留节点当前排版并登记为有证据的 `exception`，无需再次询问用户，也不因此暂停第二阶段或阻止进入已授权的第三阶段。此规则视为用户对“无目标库等价排版”的预先接受，但不降低证据要求：每条例外仍须记录节点/区间、原字体/字号/字重/行高/字距、检索过的候选和不等价原因。

- `unmapped` 只有在目标库搜索或属性比较尚未完成时使用；确认无等价资产后应自动转为 `exception`，不能长期停留在 `unmapped`，也不能再发起整批例外确认。
- 可加载字体保持真实字体和几何。字体不可加载时，若目标稿已能稳定渲染、该文字无需改写或重排、截图与边界检查通过，可保持原样记 `font-exception` 并继续；第三阶段遇到必须编辑该文字或会触发重排的组件候选时，只跳过该候选并记录原因，不暂停其他组件整理。
- 目标库实际存在等价 Style 且节点可写、本次写入造成失链、属性仍待核验、外部 Style 可无损切换、文字已重叠/裁切，或缺失字体导致目标稿无法稳定渲染时，不得转为例外。先恢复、验证或隔离受影响节点；只有问题无法隔离并会破坏整个交付范围时才停止当前阶段。

## 默认未知字距按 0px 处理

用户已预先授权：除已有有效数据中明确为非零的字距外，其余一律按字距 `0px`（等效 `0%`）处理。已有数据包括本任务正常预检顺带返回的文字区间或源样式属性；`MIXED`、缺失、不可读或未单独读取的字距直接采用 0，不以“先查清所有非零值”为前置，不要求面板证明、不再次询问，也不单独因此暂停已授权阶段。该规则覆盖本 Skill 的各阶段和后续调用，除非用户本次另有明确要求。

- **不增加字距专用扫描。** 复用已有结果，只在字体、字色、样式联动本来需要的批量读取中顺带取得字距；不为确认其是否非零而新增全量遍历、逐字/逐区间调用、源样式追查、面板检查或临时探针。仅字距为 `MIXED` 时直接采用 0，不触发分段深挖；因其他属性必须读取区间时，顺带保留其中明确的非零字距。最终必要的样式 key、布局与画面验收照常，字距仍未知时继续采用 0，不再追加读取。
- 已读到的非零字距和真实分段差异保留，不把整段混合文字统一清零。未知行高、字体、字号等不适用此规则，尤其不能把 `Auto` 行高写成 0。
- 将原始返回值与采用的 0 分开记录，依据标为 `skill-default-zero-letter-spacing`；不能声称 API 已读出 0。按此默认值继续匹配和联动，不能仅因字距仍不可读而列为 `verification-pending` 或 `exception`。
- 写入只在授权目标范围内进行，并遵守[文字样式链接保护](references/typography-layout-repair.md#文字样式链接保护)。优先由等价发布样式承载零字距；应用后不追加重复的字距赋值。确需显式设置时，仅处理尚未解析的区间，加载所需字体并验证样式 key、尺寸、换行和画面；真实冲突或失链仍须恢复或回退。此默认值不代替正式写入和验收，也不授权执行其他阶段。

## 默认文字字色归一化

`processingRootIds` 内的黑色和中性灰文字按固定 Profile 的[文字黑灰色归一化](references/yuanfudao-student-app.md#文字黑灰色归一化)自动处理。黑色/近黑文字统一为 `#333333`；中性灰文字自动绑定目标库文字用途灰阶中视觉最接近的发布 Paint Style。该规则是用户明确授权的文字字色修正：第一阶段只修改实际 Paint，第二阶段绑定真实发布 key；显式跳过第一阶段并直接执行第二阶段时，也允许在文字区间上完成这项必要的 Paint 归一化与 Style 联动，不视为补做完整第一阶段。

## 第一阶段默认接近颜色归一化

第一阶段使用固定 Profile 中的 24 项静态色板，对实际页面内的可见文字和界面 Fill/Stroke 按[第一阶段接近颜色归一化](references/yuanfudao-student-app.md#第一阶段接近颜色归一化)处理：先筛选用途相容的规范色，再选择感知色差最小且符合接近阈值的颜色，直接修正目标稿的实际 Paint，无需逐项确认。黑灰文字的专用规则优先。仅缓存端点的渐变和不符合条件的特殊 Paint 保留并说明原因。此规则只授权第一阶段的视觉修正，不授权提前搜索组件库或绑定发布 Style；显式跳过第一阶段时不补做彩色文字或非文字近似色修正。

## 三阶段工作流与确认闸门

默认只执行当前已获授权的阶段，不把后续阶段作为同一轮的隐含任务。用户首次仅提供本 Skill 和待处理节点时，从第一阶段开始；用户明确说“一次性完成三步”“完整处理”或同时点名多个阶段时，才视为已预先授权对应阶段，可以连续执行而不重复询问。用户在阶段结尾回复“同意”，只授权紧接着的下一阶段，不自动授权剩余阶段。

允许以下显式跳步路径：

- 用户说“只执行/只走第二步”“跳过第一步，只做组件库联动”或等义表达时，只授权第二阶段；完成后停止，不执行第三阶段。
- 用户说“执行/只走第二步+第三步”“跳过第一步，完成组件库联动和本地组件整理”或同时点名第二、第三阶段时，授权这两个阶段连续执行；第二阶段通过后不再等待中间确认，直接进入第三阶段。
- 用户说“帮我整理组件”“只执行/只走第三步”“只做组件整理”“不要重新链接组件库，只整理组件”或等义表达时，只授权第三阶段。其中“帮我整理组件”本身就是固定的第三阶段口令，不要求再附加“只”或“不要重新链接组件库”。核验链接目标的处理边界、共享依赖和操作前基线后，直接原位执行第三阶段，不要求历史第二阶段审计，也不执行全量 Text/Paint Style 或发布按钮联动。
- 跳过第一阶段时仍直接编辑链接目标，先记录写入范围、共享依赖和操作前基线；预检不计为完成第一阶段。首个授权阶段是第二阶段时，不执行字体、非文字实际 Paint、按钮视觉、圆角、文字重叠/裁切或其他间距修正；第二阶段仍可按本 Skill 已授权规则完成文字字色和字距解析。首个且唯一授权阶段是第三阶段时，同样不执行第一阶段修正，也不执行第二阶段样式/按钮联动。
- 跳步路径不得静默补做任何未授权阶段。若第一阶段遗留问题会阻碍发布样式等价性、按钮安全替换、组件化无损或当前阶段硬门槛，停止并报告具体节点与阻塞原因，由用户决定是否补做第一阶段。只执行第三阶段时，只因组件候选无法无损抽取、现有样式/字体/实例关系无法保持、写入范围保护或第三阶段审计失败而受阻；不得仅因缺少第二阶段历史审计而停止或改做第二阶段。

### 按工作目标识别授权范围

用户不需要知道第一、第二、第三步的名称。以下口语化表达与等义说法可直接授权对应范围；它们是语义示例，不要求逐字一致。用户明确写出的范围和排除项优先于默认路径：

- “只执行/只走第一步”“帮我做基础视觉规范”“帮我检查并规范字体、颜色、按钮、圆角和间距”“只处理基础样式和明显文字问题”只授权第一阶段，完成后停止。
- “链接组件库”“把设计稿接到规范库”“把文字和颜色接到规范库”“完成文字、颜色和按钮的组件库联动”均只授权完整第二阶段，完成后停止，不创建本地组件或整理深度结构。即使用户只在目标描述中提到文字和颜色，也仍按第二阶段完整要求处理文字、颜色和语义/状态等价的发布按钮；仅列举部分工作对象不构成缩小授权。圆角属于第一阶段，第二阶段不得调整。
- “链接组件库并整理组件”“先链接组件库，再整理组件”“把设计稿接到规范库后整理组件”“帮我检查重复结构并抽成主组件”均授权第二、第三阶段连续执行；第二阶段通过后不等待中间确认，直接进入第三阶段。不得把“抽成主组件”解释为 detach 现有 Instance。
- “帮我整理组件”是固定的第三阶段独立口令；它与“只执行/只走第三步”“只做组件整理”“组件库已经链接完成，本轮只整理组件”“不要重新链接组件库，只整理组件”等表达一样，只授权第三阶段，并先执行“只执行第三阶段时的目标预检”。
- 除“帮我整理组件”这一固定口令外，其他组件整理意图在没有“只”“不要重新链接组件库”或等义排除表达时，默认授权第二步+第三步；不得仅因用户没有主动提到组件库联动，就跳过第二步。
- “规范一下”“优化一下”“整理一下”等未指明对象的宽泛表达不授权跳步；仍按默认路径只从第一阶段开始。若用户说“完整处理”“全部规范化”或“从头到尾处理”，才授权三阶段连续执行。

### 第一步：基础视觉规范

在链接目标范围内处理：

- 字体、字号、字重和行高；可见文字及界面颜色的实际 Paint，包括按固定 Profile 将接近颜色归一化为用途相容的最近规范色；只设置视觉属性，不绑定 Text/Paint Style。
- 按钮尺寸与外观；只按已确认的视觉规则修正现有结构，不替换为发布组件。
- 已有圆角；明显的文字重叠、裁切和已确认字体问题。
- 页面及现有局部结构中主动设置的显式间距，原则上归为 4 的倍数；紧凑数字/单位的 2px 和发布资产既有约束可作为带依据的例外。
- 记录目标操作前基线、写入范围和共享依赖，并做基础截图与必要的文字几何验证。

第一阶段只读取 Profile 中已缓存的静态视觉值和用户明确给定的规范，不导入、搜索或验证发布 Style/Component key；无法脱离组件库确定的按钮状态或视觉资产保持原样，列入第二阶段候选。第一阶段不做 Text/Paint Style 绑定、发布组件替换、本地 Component/Variant、组件候选全量盘点或深度血缘/结构审计。现有 Instance 不 detach，不为第一阶段读取其完整母组件族。

## 完成优先级与验收契约

“完成”按当前授权阶段判断。用户在第一或第二阶段主动停止，不得把未获授权的后续阶段写成失败或未完成；交付必须明确“已完成第几阶段”和“尚未执行哪些阶段”，不得把第一阶段称为“组件库联动完成”，也不得把第二阶段称为“本地组件整理完成”。

用户显式跳过第一阶段时，第一阶段记为“按要求未执行”，既不算失败，也不得算作已完成。第二、第三阶段仍执行各自完整质量门槛；发现未修正的第一阶段问题时不得越权处理，只有当其阻塞当前阶段硬门槛时才将当前阶段报告为受阻并给出证据。

用户显式只执行第三阶段时，第一、第二阶段记为“按要求未执行”。直接编辑用户链接指定的目标；不要求已有第二阶段结果，不运行第二阶段全量覆盖审计，也不得把目标预检或第三阶段的局部前后值核验包装成已执行第一、第二阶段。

第一阶段的完成条件是：授权目标稿中的基础视觉检查和修复完成，已确认缺陷通过限定区域验证，授权范围外及共享资产未改，且没有文字重叠、裁切、缺失字体或未归类的显式间距问题；它不以 Style/Component key、组件血缘或最终审计脚本为门槛。

第二阶段获得授权后，文字样式和文字字色联动才成为 P0。在“第二步+第三步”路径中，该 P0 必须先于第三阶段组件抽取与深度结构整理完成；在“只执行第三步”路径中不建立此 P0，也不把未完成全量目标库联动视为第三阶段阻塞。第二阶段必须盘点当前 `processingRootIds` 范围内全部可见文字、文字颜色和文字样式状态；既有 `excludedContextNodeIds` 不得混入分母或未完成项。只有用户使用“只处理……”“不要处理……”等明确的范围限定或排除表达时才能进一步缩小第二阶段；仅说“把文字和颜色接到规范库”仍授权完整第二阶段，不能据此跳过发布按钮联动。

第二阶段及包含第二阶段的连续路径中，最低条件不是“改动了若干节点”，而是每个当前审计范围内的可见 Text 都同时具有独立的“排版状态”和“字色状态”。两类状态不能互相代替；第三阶段新建的母组件、变体和页面实例必须重新纳入同一审计，不能复用组件化前的完成数字。只执行第三阶段时不要求全量目标库覆盖，改为对所有受影响 Text/文字区间、Paint、字体和样式 ID 建立写入前后快照；未受本轮组件化影响的节点不因缺少目标库链接而失败，受影响节点的非预期样式/字体/Paint 变化和缺失前后证据必须为 0。

第二阶段及包含第二阶段的连续路径中，排版通过验收的状态只能是：直接链接目标库 Text Style、继承已验证目标库 Text Style，或带节点 ID 和已证实差异的排版例外。执行中的属性待核验（`verification-pending`）和本次操作导致的未恢复失链（`link-regressed`）必须单列为未完成项，不能改名为例外后算通过。只执行第三阶段时，排版通过验收表示受影响区间的现有 Text Style ID/key、实际字体、字号、字重、行高、字距、段落属性及几何在组件化前后保持一致，或存在已声明且可验证的组件属性覆盖；不得主动改成目标库样式。

第二阶段及包含第二阶段的连续路径中，字色状态只能是：直接链接目标库 Paint Style、继承已验证目标库 Paint Style，或带节点 ID 和证据的字色例外。仅存在任意 `fillStyleId`、Style 显示名称相同、或组件本身是远程 Instance，都不能证明字色已连接到目标库；必须验证实际 Paint Style key 属于当前 Profile/本次发现的目标发布 key 集合。只执行第三阶段时，受影响节点的实际 Paint、Paint Style ID/key、变量绑定和可见效果必须在组件化前后保持一致，或有已声明且无损的组件属性覆盖。

第二阶段及包含第二阶段的连续路径中，任何可编辑的本地文字都不能以“跳过实例”“已有同名样式”“没有完全相同的字号”或“没有精确颜色”为理由留在未分类状态。排版与字色的未分类数量都必须为 0；目标库存在完全等价资产且节点可写时，例外数量也必须为 0。确认目标库无等价排版后，按“默认保留无等价排版例外”自动登记并继续，不再等待用户逐批接受。`verification-pending` 和 `link-regressed` 也必须为 0 才能通过；否则只能交付为“未完成审计”，不能宣称规范联动完成。只执行第三阶段时不生成这些全量目标库覆盖数字，只要求受影响范围全部归类且非预期变化为 0。

**排版正确性也是完成条件**：当前授权阶段会修改或依赖的正文真实字体样式、同族文字布局、内容变长后的重叠/裁切，以及显式间距必须通过检查。第一阶段或第二阶段已授权时，已有缺陷不能因“与原稿像素一致”或已填写例外台账就算通过；普通联动/组件抽取采用像素不变验收，已确认缺陷先记录节点、证据和修复区域，再修复授权目标稿，修复区域外保持像素不变。只执行第三阶段时不主动修复原稿既有排版缺陷；若缺陷不影响组件抽取则原样保留，若候选必须编辑或会放大该缺陷则跳过对应候选并记录。若用户明确要求连缺陷也逐像素保留，则只报告冲突，不自动修复；不得据此宣称排版无问题。

## 能力边界

只处理以下三组能力，并受前述阶段授权约束：

- 第一阶段：实际字体/字号/字重/行高与 Paint、按钮视觉、已有圆角、明显文字重叠/裁切，以及授权目标稿内已确认的字体映射异常、同族文字错位、数字/单位重叠和不合规显式间距。
- 第二阶段：可见颜色的发布 Paint Style、文字的发布 Text Style，以及语义明确的通用操作按钮发布组件实例。
- 第三阶段：目标画面内重复结构的组件/组件集抽取和实例替换、语义图层命名，以及可从现有坐标精确反推的 Auto Layout/Grid 与高置信包装层整理；发布库中有真实等价组件时优先复用，否则只在目标范围内创建本页局部组件。

不要在本 Skill 中处理：

- 截图或图片转可编辑稿、HTML Capture、素材生成或重绘。
- 任意层级重排、主观间距/对齐美化，以及图标、阴影、图片、交互或适配修复；包装层清理只允许按“第三阶段深度结构整理”的高置信单子节点例外处理。第一阶段已确认的排版缺陷不属于主观美化。
- 新建设计系统、修改组件库源文件、创建近似的本地同名样式，或把本地组件冒充/替代目标发布组件。页面内组件抽取仅限本次目标稿，不回写组件库源文件。
- 仅因图层名含 `Button` 就替换卡片、列表项、导航胶囊或说明行。

颜色、文字、按钮、圆角、稳定重复结构的组件抽取、可无损整理的基础结构，以及已确认的排版缺陷，均可使用本 Skill。需要广泛结构、视觉重设计、跨页面组件库建设或组件库源文件维护时切换到 `$analyze-page-generate-design` 或专门的组件库流程。不要因为发现更多问题而扩大修改范围。

## 阶段内协议与证据复用

### 执行节奏：减少返工，保留验收

进入本次首个授权阶段前读取 [执行效率与证据复用](references/execution-efficiency.md)。同一目标稿只维护一份随阶段扩展的审计台账：第一阶段记录视觉与几何；第二阶段补充完整 Style/key 和最小实例继承信息；第三阶段再补充组件族、血缘和深度结构。显式从第二阶段开始时，台账直接以写入范围保护、基线截图和第二阶段全量 Style/key 数据建立，不伪造第一阶段记录。显式只执行第三阶段时，台账以写入范围保护、根边界、基线截图、组件候选、现有血缘，以及受影响文字/样式/Paint/字体的写入前快照建立；不重新执行第一、第二阶段，也不伪造目标库覆盖矩阵。只有写入失败、依赖不明或证据矛盾时才中途独立回读受影响范围，不为后续阶段提前收集数据；每个阶段的最终数字必须来自该阶段最后一次写入后的回读。

第二阶段按同类操作合并执行：一次紧凑预检覆盖全部可见文字、文字/非文字 Paint、现有样式 key 和按钮候选；目标发布样式按 key 去重导入并批量核验；互不依赖的 Text/Paint Style 在一次写入中完成。不要为每个文字节点、每种样式或每项检查分别发起读取、写入、面板复核和截图。最后一次写入后只做一次独立全量回读和一次视觉校验，并用同一份最终数据生成覆盖矩阵与审计 JSON。只有工具报错、回读矛盾、外部编辑或后续写入使证据失效时，才补验受影响范围。

第三阶段中，每个组件族先验证一个完整代表及实际状态差异，再批量替换。“第二步+第三步”路径保留第二阶段 P0 先行；“只执行第三步”路径保留现有样式/Paint/字体的前后值，不新增全量目标库联动。两种路径都必须验证真实组件血缘、数字长度回归、阶段像素对比与对应最终门禁，不以提速为由改成抽样验收或放宽组件搭建规则。代表验证和阶段验证在授权目标稿内连续完成，不是新增的用户确认环节。

### 0. 首个授权阶段的目标预检

1. 解析用户链接的文件与 `node-id`，直接将该节点/页面内的实际画面作为目标。记录目标 Page、根 ID/名称/父级/顺序/尺寸、`processingRootIds`、`excludedContextNodeIds`、根边界和操作前截图；保存 `baselineId` 与采集时间。
2. 核验可写范围及共享依赖，冻结待改字段原值和回退所需的节点关系。保留目标根 ID、父级和位置，不新建 Page、不复制整稿，也不为验收改变层级。
3. 直接进入已授权阶段。第二阶段只建立对应 Style/key 台账；第三阶段只建立组件候选、现有 lineage，以及受影响文字/样式/Paint/字体快照。跳步不执行或伪造前序阶段。
4. 连续阶段复用同一目标和扩展台账。每阶段以该阶段写入前基线与最终独立回读比较，运行边界验证器的 `before-after` 模式。基线、边界或共享依赖不明确时，保留相关节点并报告。

### 0A. 只执行第三阶段时的目标预检

完成上述目标预检后，直接在用户链接范围整理组件，不要求第二阶段历史审计。记录候选分类、母组件/实例 lineage、组件属性、文字区间 Style ID/key 与真实排版、Paint/变量绑定、尺寸、位置和截图。只搜索实际候选所需的等价发布组件，不批量联动 Text/Paint Style 或发布按钮。

第三阶段默认使用 `editMode="in-place"` 的前后快照与最终图片比较；用户明确要求副本时按 `safe-copy` 契约执行。代表验证可使用最小临时样本，不能把整页复制作为前置。新增/修改的母组件、变体和页面实例全部进入对应审计；这不计为执行第一、第二阶段。

### A. 第一阶段轻量预检

在尽量少的只读调用中只记录第一阶段完成所需信息：

- 目标 Page、目标根 ID/名称/尺寸、根节点 `clipsContent`/`overflowDirection`、Page 顶层节点 ID 顺序、`processingRootIds`、`excludedContextNodeIds` 和基线截图；同时记录页面根内最长子节点尺寸，但只作为内容证据，不作为目标画布尺寸。
- **基础文字台账**：遍历 `processingRootIds` 内所有可见 Text，包括实例内实际可见的 Text；记录节点 ID、字体、字号、字重、行高、实际颜色、缺失字体、包围盒、可编辑性，以及明显重叠/裁切。第一阶段不解析 Style 发布 key，也不展开完整祖先实例链。
- 可见 Fill/Stroke 的 Paint 类型、RGBA、透明度和视觉语义；现有 Style/变量只作为避免破坏的只读属性保留，不判定发布来源。
- 复用上述 Paint 读取，为符合条件的近似色记录用途、最近规范色、色差与预定修正区域；按 Profile 的接近阈值判断，特殊 Paint 与超阈值颜色记录保留原因。
- 非零圆角分布，以及可能的通用操作按钮。
- 按钮候选的语义、现有尺寸和外观；只记录第一阶段能直接确认的视觉调整，发布组件匹配留到第二阶段。
- 页面与现有局部结构中主动设置的 padding/gap/itemSpacing/段落间距，以及明显布局溢出；不做泛化命名、组件族、孤儿实例、Grid 或深度包装层审计。
- **排版缺陷台账**：实际 `fontName.family/style`、`fontWeight`、行高/字距、文字区间样式、字体变量绑定及解析值；同族文字布局规则和固定坐标的数字/单位行；页面与组件内部现有显式间距。对确认缺陷记录节点 ID、截图/几何证据、修复目标及预先限定的影响区域；修改母组件前检查关联实例是否涉及授权范围外节点。
- Profile 静态视觉值是否足以判断本次基础规范；需要真实发布资产才能判断的项目列为第二阶段候选，不进行 live key 探测。

第一阶段预检结束只生成“基础视觉问题清单”，不生成发布 Style 覆盖矩阵。完整的文字排版覆盖矩阵和文字字色覆盖矩阵在第二阶段授权后建立。第一阶段一次性探测实际使用的字体；缺失字体在目标写入前按既有字体规则处理，未验证的替代不写入。

### B. 第一阶段原位批量视觉修正

1. 完成目标预检并保存操作前基线。加载实际所需字体，缺失字体仅按已授权且已验证的字体规则处理；不能以复制或换字体来绕过未解决的字体问题。
2. 在 `processingRootIds` 中批量处理已确认的字体/字号/字重/行高、实际 Paint、按钮视觉、圆角、文字问题和显式间距；每类返回修改节点 ID。静态 Profile 无法确认的项目保留并列为第二阶段候选。
3. 保留根节点 ID、父级、顺序、位置和宽高、`clipsContent`、`overflowDirection`；不新增设计稿外层包装，不执行 fit-to-content 或按最长子节点扩高。已有实例关系保持，不为第一阶段新建组件。
4. 只有第三阶段实际抽取 Component/Component Set 时，才可在当前 Page 添加组件整理/预览 Section；不移动设计稿，不覆盖页外既有内容，第一、第二阶段不预建空 Section。
5. 写入后独立回读受影响属性与几何，以相同导出参数比较目标操作前后画面。边界 JSON 使用 `mode="before-after"`，`source`/`copy` 字段分别存同一根的前后快照，包含 `baselineId` 与递增 `capturedAt`。运行 `scripts/validate_canvas_boundary.py`，按当前阶段规则检查视觉变化后交付。

### C. 第二阶段 P0 文字与字色联动协议

获得第二阶段授权后，若第一阶段已执行则扩展其台账；若显式跳过第一步，则直接在目标稿的 `processingRootIds` 范围内建立第二阶段全量台账。只解析该范围内所有可见文字区间的 Style 发布 key、实际 Paint、最小必要祖先实例链和可编辑性，并生成“文字排版覆盖矩阵”和“文字字色覆盖矩阵”；`excludedContextNodeIds` 不计入总量或例外。两个矩阵都按 `direct`、`local-instance`、`remote-instance` 分行统计，不能合并成一个“已处理”数量。P0 阶段必须在写入后分别重新统计：

- `direct`：独立 Text 可直接设置目标 Text Style。
- `local-instance`：实例来自已有本地 Component；应追溯主组件或安全覆盖现有实例，不得整棵跳过，但第二阶段不为此新建 Component/Variant。
- `remote-instance`：实例来自远程 Component；只在确认无法覆盖或目标库无等价资产后列为例外。
- `font-exception`：字体不可用且没有可靠降级，但原节点无需编辑或重排、目标稿渲染和几何验证通过；保留原样并记录。若节点必须编辑或重排，则只隔离/跳过受影响候选；无法隔离时才是阻塞。
- `unmapped`：尚未完成目标库搜索或属性比较；这是临时阻塞状态。确认目标库无等价排版后自动转为有证据的 `exception`，不得保留为 `unmapped` 或再次请求整批确认。
- `verification-pending`：已有候选，但真实属性、字体或等价性证据不足；读取到 `MIXED`/缺失不能直接计为无等价资产。未知字距按本 Skill 预先授权采用 0，不单独计入待核验。按“默认排版值的确认”采用本 Skill 默认字距、面板或用户证据，并通过链接及画面检查的区间，不因 API 仍返回未知值而继续列待核验。
- `link-regressed`：本次写入使已记录的目标 Text Style key 非预期丢失、变成其他 key 或无法解析，且尚未恢复；经核验的预期样式切换不属于失链。必须恢复或回退，不能列为合理例外。
- `other-text-style`：`textStyleId` 可解析，但发布 key 不属于目标库。与目标发布样式完全等价时切换到目标 key；目标库无等价样式时，在临时副本验证后保留完整区间排版、移除外部库样式绑定并记有证据的排版例外。最终不得残留来源不明或非目标库 Text Style。

节点类别与排版状态分开记录。排版状态按文字区间互斥统计，失链未恢复时优先记 `link-regressed`，其他未知记 `verification-pending`；即使 `textStyleId` 非空，属性尚未核验也不计入已验证直接链接/继承。发布 key 与前后属性另列为证据。

文字字色矩阵还必须区分：

- `target-paint`：`fillStyleId` 对应的发布 key 明确属于目标库 Paint Style key 集合。
- `other-style`：存在 `fillStyleId`，但 key 不属于目标集合；即使 Style 显示名称与目标库完全相同，也不能计入目标库联动。
- `exact-unlinked`：未链接目标库，但实际 Paint 与目标发布 Paint 在语义、类型、RGBA/透明度等属性上完全等价；这是阻塞状态，节点可写时必须联动。
- `color-exception`：目标库无等价 Paint、混合字色/多段字色、特殊渐变或实例不可写；必须记录节点 ID、数量和差异证据。

第一阶段已验证且之后未受影响的字体、几何和截图证据可以复用；发布 key 和实例继承状态必须在第二阶段实读。每次文字写入仍须加载实际字体，缓存不代表字体已加载。

| 类别 | 必须动作 | 允许的最终状态 |
|---|---|---|
| 独立 Text | 按语义、字号、字重匹配并设置发布 Text Style | 直接链接，或有明确无等价资产原因 |
| 本地 Component/Instance | 查看已有主组件及其嵌套 Text；优先规范授权目标稿内的已有主组件或安全覆盖实例，不新建组件/变体 | 继承目标库样式、直接覆盖或明确例外 |
| 远程 Component/Instance | 验证 `mainComponent.key` 和现有样式；实例内 Text 可编辑且与目标样式完全等价时，在不脱离实例的前提下写入目标 Text Style；不能覆盖或视觉属性不等价时保留 | 目标库样式覆盖，或只有有证据的远程例外 |
| 缺失字体 Text | 先找语义可靠的已加载降级字体；无可靠降级时验证原节点无需编辑/重排且目标稿渲染稳定 | 直接链接、可靠降级，或默认保留的明确字体例外；需改写的组件候选单独跳过 |

文字阶段的硬性检查：

- 不允许使用“跳过所有 Instance”作为策略；只允许跳过已证明不可覆盖的远程实例。
- 远程实例不是默认例外。必须实际尝试判断实例内 Text 是否可编辑；可编辑且目标样式的真实属性完全等价时，保留实例关系并写入目标库样式。
- 不允许只按 `fontName.family === "PingFang SC"` 过滤后结束；其他字体也必须进入台账并归类。
- 不得从 Text Style 的显示名称推断字体属性。例如样式名包含 `Bold`，真实 `fontName.style` 仍可能是 `DIN-Bold`。必须先通过发布 key 导入样式，再读取样式对象的真实 `fontName.family`、`fontName.style`、`fontSize`、`lineHeight`、`letterSpacing`、`paragraphSpacing`、`paragraphIndent`、`textCase` 和 `textDecoration` 建立匹配表。
- 写入目标 Text Style 前，至少比较上述真实排版属性。普通联动只有完全等价才可直接写入；若仅字体、字号、字重相同但行高或字距不同，不得为了提高联动率改变视觉。已确认的字体/字距缺陷走排版修复路径，记录必要的本地覆盖及其与发布样式的差异；不能把带覆盖的样式算作完全等价链接。
- **默认排版值的确认**：未读到明确字距时，直接按本 Skill 预先授权采用 `0px`（等效 `0%`），无需另取面板或用户确认，也不单独触发探针。行高等其他属性仍需真实读取、对应面板或用户证据；不要把未知行高视为默认值，也不要把 `Auto` 写成 0 行高。核实发布 key、字体与字号后继续正常联动与必要验收；正式回读同时保留已有原始值与采用依据。已应用零字距样式后不追加重复赋值；明确非零字距、分段差异或画面冲突仍按真实证据处理。
- 仅字距返回 `MIXED`/缺失时直接采用 0，不假定库已损坏，也不追加区间、源样式或面板读取。其他必要排版属性存在未验证读取模式，或确需显式修改已链接文字的字体/行高/字距时，才在授权临时副本验证完整操作顺序；同一发布 key、字体/绑定模式与排版依据未变时复用已验证结果，不因未知字距重建探针、再次询问或停在临时副本。详见 [文字样式链接保护](references/typography-layout-repair.md)。
- 用户说明组件库已修复或重新发布时，旧节点/旧样式版本的 `MIXED` 与历史错误立即失效。先按原发布 key 批量重新导入当前样式并读取真实属性；当前样式已明确为目标值时，直接批量重新绑定并进入最终回读，不再沿用旧结论、重复探针或强写节点字距。当前重新导入仍异常时，才按文字样式链接保护继续诊断。
- 修改字体、行高、字距、相关变量或派生组件时，在同一写入调用的返回中逐项核对受影响文字区间的目标 Text Style key，不为每个节点另发独立调用。非预期失链属于写入失败，须定位操作并恢复链接或回退；全部写入完成后的正式结论仍来自一次最终独立全量回读与视觉校验。重新应用样式后同时复核真实排版与截图，不能只补回 key；不得把本次造成的未恢复失链移入例外台账结束。
- `400`、CSS 声明、字体变量名称或一次 `loadFontAsync()` 成功都不能单独证明字形正确。正文应核对真实 Regular 字体、解析后的字重、行高/字距和编辑器实际显示；不要把 400 改成 500 来掩盖偏细。可疑绑定仅在受影响节点上记录后处理，不批量清除正确变量或压平混合字体。
- 文字颜色与字号必须分别统计。颜色未映射不能让字号映射也被跳过，反之亦然。
- 对字色而言，`fillStyleId` 非空不代表合格。必须通过 `getStyleByIdAsync(fillStyleId)` 读取发布 key，并与 Profile/本次发现的目标 Paint Style key 集合核对；显示名称只用于报告，不能用于判定来源。
- `other-style` 的实际 Paint 若与目标发布 Paint 完全等价，必须按目标发布 key 导入并替换；不能因为它已经有样式、来自远程组件或名称相同而保留。远程实例内 Text 可写时，保留 Instance 关系并覆盖 `fillStyleId`。
- `other-style` 与目标库没有等价 Paint 时，不保留来源不明的外部库绑定。在授权目标稿的临时副本中保存实际 Paint、移除 `fillStyleId`/`strokeStyleId`、回读并确认像素一致后，再应用到交付节点并记为字色例外；无法无损解除时标记 `verification-pending`。最终 `other-style` 必须为 0。
- 字色匹配先判断语义，再比较完整 Paint：Paint 类型、RGB/RGBA、Paint opacity、visible、blendMode；渐变还要比较 stops、透明度和 transform。只比较 hex 值不足以证明等价。
- 当 Text 的 `fills` 或 `fillStyleId` 为 `figma.mixed` 时，使用 `getStyledTextSegments()` 按文字区间建立台账；不得把多段字色按一个 Text 节点粗略计为已链接或例外。
- 写入后必须再次核对目标 key、实际 Paint 和颜色变量绑定。`exact-unlinked`、`other-style` 中可无损切换的数量，以及未分类字色数量都必须为 0。
- 进入组件抽取前，`unclassified`、`unmapped`、`verification-pending`、`link-regressed`、`other-text-style`、`other-style` 必须全部为 0。`unmapped` 须通过真实库查询和等价性核验转为已验证链接或有证据的例外；不能仅为清零将未知或失链转为例外。若仍有可编辑、完全等价且可写入的文字未链接，必须停在文字阶段。
- 只导入发布 Text Style 不算完成；必须验证写入后的 `textStyleId`、组件继承关系或明确例外证据。

### D. 第二阶段批量链接文字与颜色

可以在一次写入中处理文字和颜色，但两类要独立统计和返回。圆角已在第一阶段处理，第二阶段不得为了 Style 联动重复改圆角。

文字：

- 按“语义 → 字号 → 字重”匹配，不只按距离最近的字号。
- 源稿属于宋体/中文衬线类时，按[宋体必须使用思源宋体](references/typography-layout-repair.md#宋体必须使用思源宋体)使用真实可加载且与原字重一致的思源宋体，优先核验 `Source Han Serif CN`。所需字重不可用时保留原稿并报告具体阻塞，不改用 PingFang 或其他字重。保留字号、行高、字距、对齐和混合区间；目标库无完全等价 Text Style 时记录有证据的字体/排版例外，不为联动样式改变字体。
- 标题、正文、说明、数字价格使用对应体系；没有等价样式时保留并报告。
- 只通过发布 key 导入并应用 Text Style；不要创建本地近似样式。

颜色：

- 文字黑灰色先按固定 Profile 的“文字黑灰色归一化”处理：黑色/近黑统一为 `#333333` 并链接 `中性色/Color_Gray_02`；其余符合条件的中性灰按感知明度匹配最近的文字用途灰阶发布 Style。即使本轮显式跳过第一阶段，这项用户预授权的文字 Paint 修正仍在第二阶段执行。
- 先按用途匹配，再比较颜色距离：标题、正文、说明、边框、模块背景、页面背景、品牌强调分别处理。
- 先由 Profile/受 `includeLibraryKeys` 限定的搜索结果建立目标 Paint Style 发布 key 集合；所有现有 `fillStyleId`/`strokeStyleId` 都必须按 key 判定为目标样式、其他样式或未链接，不能按名称判定。
- 只给可见且等价的 Paint 绑定目标发布 Style。已有其他库/旧版本同名 Style，但实际 Paint 与目标样式完全等价时，切换到目标发布 key。
- 半透明色、图片、渐变和特殊装饰色没有等价资产时保留原 Paint；不得为了提高联动数量而丢失透明度或视觉效果。
- 应用 Style 后确认目标 Style key 命中，并确认没有旧的颜色变量绑定残留。

### E. 第二阶段替换发布按钮

- 只替换触发业务操作且有真实等价状态的按钮。
- 优先导入明确的 variant component key；组件集合属性不可读时，不访问损坏的 `variantProperties`，改用已验证的子组件名称/key。
- 候选排序固定为“语义 → 高度差最小 → 类型/状态”；不得仅为了获得某个状态而选择高度更远的组件变体。
- 组件变体的原生宽度不参与选择；实例宽度可独立覆盖，设置为最接近原按钮宽度的 4 的倍数，组件规范要求固定高度时以目标组件真实高度为准并检查布局影响。
- 先确认文字是否由组件属性管理；无 TEXT 属性且文字节点没有属性引用时，加载组件实际字体后再直接覆盖文字。
- 同高度状态不存在时，不得跳到更远高度只为取得状态；若最近高度组件可通过实例透明度等可审计 fallback 保持视觉和语义，可使用该组件并在名称和交付中说明，否则保留原结构，只联动其中的颜色、文字和圆角并报告原因。

### F. 第三阶段页面内组件抽取

组件抽取与“连接发布组件库”是两件事：只针对实际组件候选搜索并复用目标库中真实等价的发布组件；没有等价资产时，才在目标范围内创建局部组件，不修改库源文件，也不把局部组件伪装成发布库组件。只执行第三阶段时，这项搜索不授权 Text/Paint Style 或通用按钮的全量联动。

**先按共同结构识别业务组件族。** 比较完整模块的共同骨架、文字角色、内容槽位和布局责任，不要求原图层树、文案、素材、顺序或高度完全相同。先记录共性，再把差异分配到属性、可选区域或真实状态；不得把各自只出现一次的内容配置拆开统计，从而把同族模块判为“没有重复”。具体建模与本次课程报告示例见 [组件族建模](references/component-variant-lineage.md#先决定需要几个母组件)。

- 标题、说明、数字、按钮文案不同，用 TEXT 属性；图片、插画、优惠券和其他内容区域的有无，优先用 BOOLEAN 显隐；已有子组件的替换用 INSTANCE_SWAP。通过 Auto Layout 让隐藏区域退出排版，保留各实际实例原有位置、尺寸和视觉，不让隐藏内容留下空白。
- 图片在标题上方与内容区在标题下方，可以作为同一母组件的两个可选槽位。文字或显隐造成的自然高度差不构成拆族、跳过或新增尺寸 Variant 的理由；真实业务状态或无法由可选槽位表达的布局差异才使用 Variant。
- 用户明确指定同类状态模块做组件集时，建立同一 Component Set，用状态属性管理；本次“体验课暂未解锁 / 本节课已开放”必须是一个课程空状态组件集的两个状态，不以多个互不关联的母组件或只完成其中一个状态代替。
- **已有组件库按钮直接复用，不新建本地按钮组件。** 已有库实例保留原血缘，嵌套到业务组件中；手工按钮先核验对应原始发布组件及合法实例覆盖，只在当前业务候选内无损复用。不能因单个发布候选的 Paint、尺寸或文字属性不同，就另建本地按钮。尚未找到或无法无损复用时，保留并记录该依赖的具体未完成项，不扩大为第二阶段全量按钮替换。

组件来源必须在 Figma 内直接可识别：

- 目标范围内新建的 Component/Component Set 统一使用 `本页局部/<语义名称>`；组件整理 Section 统一命名为 `本页局部组件｜不属于发布库`。组件 `description` 写明“来源：当前目标稿；不属于发布库「<目标库名称>」”。不得在本地组件名称中使用目标发布库名称或与发布资产完全相同、容易混淆的路径。
- 发布组件和发布 Style 保留官方名称，不改名。“第二步+第三步”路径在审计中为每个实际使用的 Text Style、Paint Style 和 Component 记录来源；“只执行第三步”路径只记录本轮实际复用的发布 Component 和新建局部 Component/Component Set，并对受影响节点保留既有 Style 前后快照，不把既有 Style 重新归类为本轮目标库资产。来源字段包含 `nodeId`、资产类型、显示名称、`sourceType`、`libraryName`、`libraryKey`、资产发布 key、`remote` 和使用数量；`sourceType` 只能是 `target-library` 或 `local-copy`。本地资产的库字段为 `null`、`remote=false`，发布资产的库字段必须与本次锁定目标库一致。

创建组件前必须先完成“组件族数量判定”：记录共同骨架、差异字段及其属性映射，分别声明组件族数、Component Set 数和其中的 Component/Variant 数，不能把“一个组件族”误写成“只能有一个状态组件”。仅文字或可选内容不同、没有独立状态要求的同族模块优先使用一个母组件；禁止按每条文案建独立 Component/Variant。用户指定的状态组件集及真实业务状态使用明确的 VARIANT 属性，文字和区域显隐仍各自由 TEXT/BOOLEAN 管理。

若预检发现本地实例的原始组件缺失、已移除或无法从当前文件追溯，必须读取 [component-variant-lineage.md](references/component-variant-lineage.md)，先对全部同构实例做一次性分组，再按每个组件族恢复一个母组件并迁移全部实例；不得从每个实例分别恢复母组件。远程发布组件无法解析时不得伪造本地同名母组件，应停止替换并报告。

只把满足以下条件的候选抽成组件或组件集：

- 至少有两个共享业务骨架的模块，或有明确的同族业务状态；不以完全同构或高度相等为前提；
- 共同职责、内容槽位、边界和主要样式可以稳定建模，差异可以由 TEXT/BOOLEAN/INSTANCE_SWAP/VARIANT 属性表达；
- 组件化后能保持原实例的尺寸、位置、圆角、文字换行和图片/矢量边界；
- 候选名称可以从内容和职责确定，例如“指标卡”“词汇标签”“统计卡”，而不是 `Container` 或编号。

组件阶段不能以“内容、顺序、高度、插画或背景不同”为跳过依据。先验证共同骨架加属性与可选槽位，再按需要建立状态组件集。只有真实不属于同族的对象才记为不适用；已确认同族但实现或验证受阻的候选记为 blocked/pending，不能改为跳过。首次实例子层坐标或属性覆盖失败只说明当前实现路径受限，须按组件建模参考检查母组件布局、槽位及变体定义路径后再判断。若重复候选盘点已确认存在稳定同族结构，则新建组件数量为 0 必须视为未完成，而不是正常结果。

图标组件化边界：图标组件化不等于重绘或修改图标。重复出现且职责相同的图标 INSTANCE 或单一图标向量，至少应作为原始图标 Component，或复用已验证的发布库图标 Instance；保持原始路径、填充、描边、尺寸和边界。一次性装饰图标、完整插画和职责不稳定的图标只记录跳过原因，不强行组件化。

不得抽取根画布、整页背景图片、完整 IP/插画、装饰星光、单次出现的复杂价格组合、只承担裁切/叠层/命中区职责的包装层，或边界无法稳定保持的 Absolute 组合。

组件阶段按以下顺序执行：

1. 基于第三阶段目标操作前基线盘点完整业务模块的共同结构，重复子树签名只作辅助。记录候选节点、同族数量、共同槽位、差异属性映射、尺寸和视觉边界；必须覆盖每个 `processingRootIds` 当前可见范围内的重复业务模块，不遍历 `excludedContextNodeIds`，也不凭名称含 `Card`、`Tag` 或 `Component` 就抽取。背景和内容为兄弟节点的完整卡片同样纳入，不只抽内部文字或按钮来代替整卡组件化。
   盘点明确列出“已有组件 / 待建单母组件 / 待建状态组件集 / 不适用及理由”；执行后的失败候选另列 blocked/pending，不混入不适用。任何候选不得只留在模型内部判断。
2. 为业务组件族选择代表建立共同骨架；文案用 TEXT、可选图片与内容区用 BOOLEAN、子组件替换用 INSTANCE_SWAP。用户指定的状态集、真实业务状态或固定规格使用 Component Set 和明确的 Variant 属性；自然高度差不单独产生 Variant。已有库按钮作为依赖复用。嵌套库子层无法暴露为外层属性时，按参考处理安全嵌套覆盖或局部建模，不按文案另建组件。已授权的确定排版缺陷先走修复路径，不重复索要同一授权。
3. 批量替换前先跑通该族的完整代表：创建母组件、仅在确有变体时派生状态并组合组件集、创建实际页面实例，验证属性覆盖、最终样式 key、血缘、尺寸与像素；涉及数字行时一并完成内容长度回归。实际画面中已显示或用户明确要求的状态，其可见性、嵌套尺寸等差异都须覆盖；不检查未使用的隐藏状态，不能只验证孤立母组件。通过后再用新组件实例替换同组重复节点，保留原顺序、坐标、尺寸和可见性；实例宽高只在能证明视觉不变时覆盖。组件内部字体和文字属性变更前加载真实字体。
4. 返回所有创建、替换、删除和被修改节点 ID，并建立“原节点 → 组件/变体 → 实例”的映射；无法保持边界或属性职责不清的候选只报告，不抽取。
5. 使用与组件化前相同的节点、尺寸和截图参数对比 PNG；普通组件抽取先按字体与视觉容差检查；出现未被接受的视觉差异、换行、裁切、重叠或图片变化时，只修复或回退对应组件组。原有排版缺陷须先走修复路径并保存通过后的基线，再验证组件抽取本身无损，不把原有重叠当作需要保留的几何。

每个组件族的一批写入后，独立回读新增/修改的 Component/Component Set、嵌套变体及全部受影响页面实例。“第二步+第三步”路径按“第二阶段 P0 文字与字色联动协议”重新审计受影响范围，沿 lineage 比较派生前后目标文字样式 key，并更新台账与覆盖矩阵；本轮 `unmapped`、`unclassified`、`verification-pending`、`link-regressed`、可无损切换的 `other-style`/`exact-unlinked` 和未处理本地实例文字必须为 0。“只执行第三步”路径沿 lineage 对比受影响文字区间、Style ID/key、实际排版、Paint、变量绑定、字体和几何的前后快照；非预期变化、无法解释的失链和缺失前后证据必须为 0，不要求未受影响节点或原有样式改绑目标库。两种路径都按执行效率参考追踪影响范围，不重新扫描已证实未受影响的其他族；每次可能导致失链的操作仍立即核对受影响区间，不能攒到整批结束。组件化前的统计不能充当新节点证据。

抽取后归并：对本阶段新建 Component 做共同结构复核；仅文案、可选图文区域或自然高度不同的同族内容归入单母组件属性，用户指定或真实业务状态归入同一 Component Set。不得按文案或显隐组合穷举 Variant。无损归并尚未通过的必要候选保持未完成，不以保留独立组件宣称族建模完成。

同族卡片若由一个负责完整边界的 layout/background Frame 与内容层组成，直接把该 layout 作为母组件根；根节点承载背景填充、圆角和尺寸，内容层作为其直接子项。禁止在已有 layout 外新增无职责包装或把背景 Frame 作为页面孤立节点；承载真实 Variant 身份和可见共享母实例的最小外层 Component 属于有效职责，具体边界责任按组件建模参考分配，不重复承载背景或圆角。状态构建按组件建模参考选择可验证的共享骨架或嵌套母实例路径，不强制所有 Variant 由实例转换；已有库实例不得解绑，不得隐藏整个母实例或叠加另一套内容伪造状态。

同一语义的统计卡、指标卡或信息卡，即使分类名称、数字、图标显示、背景色或真实高度不同，也必须进入同一组件族复核。分类、状态和是否显示图标等结构差异使用 VARIANT/BOOLEAN/INSTANCE 属性；数字、标题、分类名称和统计文案使用 TEXT 属性。背景层与内容层不得作为孤立页面 Frame 遗留，除非记录无法安全合并的具体原因。

组件整理/预览区的 Component Set 必须有真实可见的虚线边界：使用可见 Stroke Paint 和非空 `dashPattern`，并验证虚线覆盖整个变体集合边界。该描边只允许存在于独立的组件整理/预览区，不得写入设计稿页面实例或变体内部；颜色、粗细沿用已有预览/标注样式，不擅自新增未验证的固定值。

视觉比较规则：普通联动、组件抽取和结构整理按 [字体与视觉容差](references/font-visual-policy.md) 使用固定 text-edge-v1 规则。合格轻微字形差异自动记录并继续；意外的布局边界、文字换行/基线、图片或矢量裁切、可见性和重叠变化须修复或回退受影响候选，独立候选继续。已确认缺陷修复检查预先限定的区域、真实几何和可见效果，不能把任意变化事后归为修复。

组件抽取完成后，再进入结构阶段。组件内部现有及新增的显式间距与页面采用同一规则；同族数字/单位行还须通过内容长度变化回归，不能只验证组件血缘。

#### 组件集的共享维护

组件集的兄弟 Variant 均为主组件，第一个仅是默认状态，不自动成为其余变体的母组件。对共同骨架稳定、需要共同维护的状态族，优先复用或建立集合外的共享基础组件／共享子组件，让各 Variant 嵌套其可见实例；声明共享字段与状态覆盖字段，并按 [共享基础组件与同步验收](references/component-variant-lineage.md#共享基础组件与同步验收) 完成真实改动、独立回读及恢复。仅复制骨架或放入同一 Set 不能算共享同步通过；不强制所有组件集嵌套整卡基础组件。

用户仅授权某族小样本验证时，只处理该族及其必要依赖，不扩大为整页第三阶段。优先复用已有正确血缘，不为演示重建组件；记录引用范围，临时改动恢复后核对目标与其他组件保持原样。交付只声明该族实际通过的项目，不声称全页组件整理或未测试属性已通过。

#### 组件族变体来源

当多个节点被判断为同一母结构的重复候选、存在多个疑似同族组件、母组件丢失，或母组件内部包含需要覆盖的远程 Instance 时，读取 [component-variant-lineage.md](references/component-variant-lineage.md)，按其中的组件数量判定、母组件恢复、属性降级、母组件派生和回归检查处理。该规则不改变正常的目标编辑、样式联动或组件库搜索路径。

### G. 第三阶段深度结构整理

先截取完成本轮组件抽取后的目标稿，作为结构阶段基线。普通无损整理只修改 [references/structure-fast-path.md](references/structure-fast-path.md) 判定为高置信的候选；已确认的文字/数量行和间距缺陷按 [排版修复路径](references/typography-layout-repair.md) 处理，两者分别记录基线和验收结果。只执行第三阶段时，不主动修复原稿中既有的第一阶段排版或间距缺陷；若候选必须修改相关文字且无法保持现有排版，跳过该候选并记录原因：

- 按真实内容和容器职责，把泛化或错误语义图层名改为可理解的名称。
- 只有单子节点、无 Fill/Stroke/Effect/Clip/Mask/命中区/交互职责，且删除后可唯一恢复子节点边界与父级布局责任的冗余包装层，才可按结构快速路径清理；必须把原有 padding/gap 责任补回正确父级。
- 结构阶段必须对识别出的候选包围 Frame 逐项记录“清理”或“保留”及职责原因；只对满足上一条条件的无职责包装层清理，不以统一层级或减少 Frame 数量为目标。
- Auto Layout 父层的逻辑子项被全部设为 Absolute，且现有坐标能精确还原为 padding/gap 时，恢复为流式子项。
- Grid 使用零宽占位轨道并把中间控件设为 Absolute，且真实轨道宽度、顺序和对齐可由现有边界精确反推时，改为真实 Grid。
- 页面、母组件、变体和实例内部，现有及新增的显式 padding/gap/itemSpacing/段落间距均检查整数偶数，优先 4 的倍数；紧凑数字/单位可用 2px。0px 是新建普通文字的默认字距，也是本 Skill 对未读到明确字距的默认采用值；已有文字的明确非零字距和真实分段差异保留，确认缺陷后才按排版修复路径处理，不全量重写为 0。只规范主动设置的间距，不对自然字宽、HUG 尺寸或基线计算产生的坐标统一取整；发布库约束或用户明确要求的差异逐项记录，不能静默排除组件内部。

除上述高置信单子节点例外外，不要删除包装层；不要转换根画布、装饰叠层、图片、角标或复杂价格组合。职责明确的“数值 + 分母/单位”行可按排版修复参考改为基线对齐的自适应布局。字体缺失先修复真实字体并重新测量，不能通过扩大容器或 Auto Layout 掩盖字体错误；无法可靠修复时报告阻塞。

结构写入后用相同截图参数和对应阶段基线比较。普通整理的像素差异须定位并回退；缺陷修复区域内只允许预先声明的变化，区域外必须像素一致，不能事后扩大区域掩盖误改。

### H. 分阶段最终验证

第一阶段最后一次写入并独立回读后，只生成轻量阶段记录：目标节点及操作前后记录、修改与保留清单、字体和文字几何结果、显式间距结果、相同参数截图及下一阶段候选；不运行要求发布资产覆盖率的最终审计脚本。

第二阶段最后一次写入后只执行一次独立全量回读与一次视觉校验，再按 [最终审计契约](references/final-audit-contract.md) 从该最终数据生成机器可读 JSON；组件 mutation 均为 0，并运行 `python3 scripts/validate_final_audit.py <audit.json>`。“第二步+第三步”路径在组件/结构全部写入后重新生成同一完整 JSON 并再次运行该验证器。“只执行第三步”路径不使用第二阶段最终审计契约，改按 [只执行第三阶段审计契约](references/third-stage-only-contract.md) 生成组件审计 JSON，并运行 `python3 scripts/validate_component_audit.py <audit.json>`。若回读后又发生写入、外部编辑、失败或证据矛盾，旧结果失效，只补验受影响范围并重新生成最终结果。对应验证器退出码 0 才能宣称当前授权阶段完成；退出码 2 表示审计结构有效但阶段仍未完成；退出码 1 表示审计自身无效。不得忽略门禁结果或手工改写完成状态。

## 停止与回退条件

与当前授权阶段相关的任一条件成立时停止快速写入，转入重新发现或向用户报告；后续阶段专属条件不得反向阻塞第一阶段：

- 目标节点不是可遍历的可编辑节点。
- 第二阶段或包含第二阶段的路径所需 Style/Component key 无法导入或类型变化；只执行第三阶段时，只有实际组件候选所需的发布 Component 无法核验，或受影响节点的既有 Style/Component 血缘无法保留，才阻塞对应候选。
- 第二阶段或包含第二阶段的路径中，文字样式属性经区间与编辑器核验仍无法确认，且不属于已按本 Skill 默认采用 0 的未知字距，或样式重应用与排版修复相互冲突。只执行第三阶段时，不重应用样式；若受影响区间的前后样式/字体/Paint 无法确认，则回退或跳过该组件候选。未知字距本身不构成停止条件，真实冲突也不能通过重复强写字距或修改库源文件绕过。
- 第二阶段组件库自身存在错误，且没有已验证的子组件 key 可用。
- 字体缺失且没有语义可靠的降级、无法保持原节点稳定渲染，或必须编辑/重排又无法把受影响候选安全隔离。
- 第二阶段替换按钮会明显改变布局或视觉，但组件库没有等价状态。
- 第三阶段普通无损结构候选不能从现有坐标精确反推出布局；已确认缺陷也无法确定可靠的字体、布局职责或修复范围。
- 当前阶段普通整理存在不符合 text-edge-v1 的视觉变化且无法修复或回退，或缺陷修复改变了限定区域外的像素。
- 第三阶段重复候选不足两个、组件边界不稳定、属性职责无法确定，或组件抽取本身会改变已通过修复的视觉/布局。
- 第三阶段组件化后存在不符合 text-edge-v1 的视觉变化且无法修复或回退；数字变长仍重叠、裁切或间距不一致。
- 两次操作因同一外部原因失败。
