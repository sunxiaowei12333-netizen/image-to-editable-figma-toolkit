# 图片转可编辑Figma文件

## 目标

把用户提供的界面图片还原成可预览、可交互、图层语义正确的 HTML 页面，再从正确的本地 HTML 页面采集到指定 Figma 文件。纯场景背景保留为一张独立位图；完整 IP、复杂画框、复杂礼物和其他无需编辑内部结构的完整视觉原子保留为独立图片；简单 UI、几何图形、图标和需要更新的文字交付为原生矢量形状、Vector、Text 或 Group。可独立替换不等于必须矢量化，编辑粒度应停在有实际编辑价值的视觉原子边界。每个任务内部保留小体积、可维护的源 HTML，但对外只交付一个 `*-capture.html` 双通道文件：体积安全时使用自包含模式；官方 Capture 的序列化载荷有超限风险时，改用同一版本目录中未经压缩、缩放或改色的本地图片/字体资源。普通 HTTP URL 用于预览和浏览器插件，官方 Capture 在同一 HTTP URL 附加参数后条件加载官方脚本；只有自包含模式额外保证 `file://` 单文件可移植。HTML 审批阶段必须同时向用户提供一个明确预览链接和一张当前版本的最终预览图，不并列展示内部源文件、文件卡片、构图报告或第二个 HTML 入口。

## 时间与质量服务等级

把 `30 分钟` 作为包含 HTML、视觉校验和 Figma 导入的标准目标，不把它解释为必须牺牲清晰度的硬截止时间。任务开始后 5 分钟内完成资源清单、素材来源判断和复杂度分级，并在预计超过 30 分钟时主动报告预计完成时间与主要原因；不得静默运行数小时。

- **轻量，20–30 分钟**：参考图清晰，主要素材可直接复用、干净裁切或抠图，最多需要 1 个简单图片编辑任务，字体和 Figma 通道无异常。
- **中等，30–45 分钟**：需要 1–2 个生成/修补任务，存在复杂透明前景、少量遮挡补全或字体映射，但可在一次综合预览后收敛。
- **复杂，60–90 分钟**：确实需要 3 个以上全新生成资源、严重遮挡补全、源图有效分辨率不足，或 Figma/字体通道发生异常。命中后必须在继续重型生成或导入前报告，不得仍按 30 分钟承诺。

到达当前等级的预计时间时，如果下列质量门槛尚未通过，保留已有正确产物并报告未通过项和新的预计时间；不得降低生成模型、输出分辨率、采样质量或 Figma 验收标准来凑时间，也不得把低清或伪透明资源作为“先交付版本”。

### 位图质量硬门槛

- 新生成、重型编辑和可替换源裁切的有效像素宽高以最终显示尺寸的 `2×` 为首选，两个方向中的最低有效倍率不得低于 `1.5×`。`1.5×–<2×` 记为“接近 2×”并记录实测倍率，可正常进入最终画布 `100%`/`200%` 清晰度检查，不再作为异常单独阻断；低于 `1.5×` 只允许用于不可替代、没有更高质量来源且插值不能恢复真实细节的源素材，并继续作为已记录例外等待用户明确验收 HTML。不得把插值放大伪装成有效倍率。
- 在最终标准画布的 `100%` 和 `200%` 预览中检查清晰度：不得出现可见模糊、锯齿、压缩块、脏边、底色光晕、错误文字、乱码或因缩放产生的细节崩坏。
- 透明前景必须具有真实 alpha；不得把棋盘格、纯色底、原截图背景或相邻 UI 烘焙进资源。重要主体不得被截断，alpha 边缘不得存在明显离群像素或半透明残渣。
- 透明前景除来源中真实存在的镂空外，主体内部不得出现新增透明岛、缺口或被背景色穿透的区域。浅色、白色、高光、发光区域以及人物的手指、头发、服饰和手持道具必须逐项核对；alpha bounding box 正确不能代替内部完整性检查。
- 可编辑 UI 文案必须保留为 Text；若固定印刷文字属于完整视觉原子内部，则必须正确、清晰且与参考图一致，不能用 HTML 叠字掩盖图片缺陷。

## 强制约束

- 未收到用户明确的具体尺寸或设备类型/方向要求时，判定画布必须优先比较宽高比，而不是根据原图像素大小判断设备类型；原图像素大只代表分辨率高，不代表它是 Pad。
- 用户明确指定具体尺寸，或明确描述要生成 Pad/平板、手机横屏、手机竖屏设计稿时，必须优先遵循用户要求，不得因原图比例自动改判设备类型；未明确指定时，才将原图宽高比依次与横屏手机 `812 ÷ 375 ≈ 2.165`、竖屏手机 `375 ÷ 812 ≈ 0.462`、Pad `1024 ÷ 640 = 1.6` 比较并采用比例最接近的标准画布。未提供具体尺寸时，Pad/平板使用 `1024 × 640`，手机横屏使用 `812 × 375`，手机竖屏使用 `375 × 812`。
- 在未明确指定设备类型/方向时，若原图是某个标准画布的等比例倍数，必须还原到该标准画布。例如 `1624 × 750 = 2 × (812 × 375)`，应判定为横屏手机 `812 × 375`，不得因其像素尺寸较大而判定为 Pad。
- 在未明确指定具体尺寸或设备类型/方向时，仅当宽高比没有明显匹配、且画面形态接近 Pad 时，才默认使用 `1024 × 640`；接近横屏手机比例时使用 `812 × 375`，接近竖屏手机比例时使用 `375 × 812`。
- 新任务在生成资源或编码前必须读取 [references/composition-fidelity.md](references/composition-fidelity.md)，并在任务版本目录建立 `composition-contract.json`。至少记录高视觉权重对象和重复主体的 `selector / count / anchor / target bounds / aspect policy / z-order / expected Figma type`；主体数量、锚点和锁定比例属于 Capture 前硬门槛，不得只凭整体观感判断。
- 新任务还必须在资源生成前完整读取 [references/resource-routing.md](references/resource-routing.md)，计算每张参考图的 SHA-256，并建立 `resource-manifest.json` schema v3。清单逐项记录前景视觉原子的 `kind / compositionId / data-resource-id / editableInternals / complexitySignals / expectedFigmaType / sourceMethod / fallbacks`；选择 `clean-crop` 或 `reliable-separation` 时还必须记录并通过 `reuseEvidence`。在生成或编码前运行 `python3 scripts/preflight_resource_plan.py <resource-manifest.json>`；提取证据缺失或任一必要条件为 false 时必须改用参考图编辑/生成等合规图片方案，不能先做页面再观察效果。完整人物、复杂画框、材质装饰和独立插画的图片路由属于 Capture 前硬门槛；普通按钮、表单、规则卡片和标准 UI 图标仍按原生节点规则处理，不得因本门槛过度位图化。
- 参考图与目标标准画布宽高比不同时，目标画布仍按上述优先级确定；完整人物、IP、画框、主面板和其他视觉原子保持自身比例与语义锚点，通过延展/裁切纯场景背景、调整留白和重新排布适配。禁止拉伸整张参考图，禁止为填满画布改变主体数量或复制前景。
- 人物、头像、商品、卡片和其他可识别主体的最终数量必须与构图契约一一对应。生成器、抠图、裁切或 Capture 意外产生额外主体、重复影像或相邻场景内容时立即拒绝，不进入下一阶段。
- 气泡、牌板、标签和其他高视觉权重不规则形状必须在构图契约记录轮廓不变量，例如尾巴/凹口方向与位置、长宽比、描边层数和圆角。不得用未标记的 `::before`/`::after`、CSS 盒子或 `clip-path` 近似一个最终需要作为 Vector/Line 编辑的轮廓。
- Figma 导入是 HTML 验收后的第二阶段。每个任务都必须先完成内部源 HTML、对外双通道 Capture HTML、构图报告和最终截图并经过用户明确审批；审批前不得新建 Figma 文件、创建 Capture ID、调用插件导入或写入任何 Figma 节点。审批的判定、失效与重试规则以标准工作流中的“HTML 审批门”为准。
- 需要生成纯背景或前景图片资源时，按以下顺序选择生成通道：优先调用 `image-gen` 并使用 `image2` 模型；`image2` 不可用但 `image-gen` 可用时，使用 `image-gen` 当前可用的最高质量图片模型；`image-gen` 工具不可用时，直接改用当前环境中已有且能够完成该任务的生图或图片编辑模型。首选工具或模型缺失只属于路由降级，不算该视觉原子的生成失败或重试次数，不得仅因此暂停或结束任务，也不得要求用户先补装指定工具、配置 API 或另行授权。调用任何图片生成工具前仍先加载 `imagegen` skill；若其中的工具可用性或 fallback 限制与本条冲突，以用户为本 Skill 明确指定的这条降级链为准。所有通道沿用相同的最终级提示词、参考图、目标画幅、透明度、分辨率、视觉原子完整性和 QA 门槛，并为前景图片输出透明 PNG。简单几何和确有内部编辑价值的简单装饰优先使用 SVG，不要先生成 PNG 再追踪；标准图标的 SVG 只允许作为 Hugeicons/Icon Library 的渲染结果，不得手写路径或先生成 PNG 再追踪。风格扁平本身不构成必须矢量化的依据。
- 对只有合成截图、没有独立原始素材的完整 IP/人物、复杂画框和复杂礼物，先判断边缘是否适合可靠分离。只有轮廓清晰、硬边、背景可明确区分且不含头发、手指、浅色/白色高光、发光道具、半透明材质或复杂镂空时，才优先使用通用抠图/分割；命中任一脆弱边缘特征时，跳过通用自动抠图，直接使用参考图生成/编辑完整视觉原子。不得为了节省生成时间，先用 GrabCut、全局 HSV 删色或颜色阈值处理这类复杂对象。
- 先按当前生成工具和版本已经验证的能力选择首次透明资源通道：有真实 alpha 成功记录时，首次调用直接生成/编辑 RGBA 透明 PNG；没有可靠记录，或同一工具/版本已经返回过无 alpha 文件时，为避免失败后再生成一次，首次调用直接使用与主体色域差异最大的单一高饱和纯色色键背景，并在进入色键分支时先完整读取 [references/alpha-extraction.md](references/alpha-extraction.md)。浅绿、白色或发光主体禁止使用白、灰、绿、青背景，默认使用已有成功记录的纯洋红 `#FF00FF`；其他主体逐项选择不进入其固有颜色、不透明边缘、浅色/白色高光、发光区域、道具或半透明材质的高对比色键。最终落点背景只用于合成后的色边验收，不参与生成前色键排序或优先级。没有安全色键时改用真实 alpha 或其他合规图片方案，不得强行选色。资源清单只记录主体冲突检查、最终精确色键及选择依据，不生成多张候选。提示词写有“透明背景”不能代替实际文件 alpha 验证。
- 优先使用生成器直接产出的真实透明 PNG，并以文件实际通道确认 `hasAlpha=true`。若首次结果只有烘焙棋盘格、意外白底或其他并非预先选择的纯色底，保留原始文件并拒绝把它当成透明资源；不得对浅色/白色主体或发光画框使用白色距离阈值补救。只有首次即按前条选择了可分离色键、且色键未进入主体时，才允许后续分割；生成完成后继续按已读取的 [references/alpha-extraction.md](references/alpha-extraction.md) 执行。生成器产出的色键文件必须以 `scripts/extract_colorkey_alpha.py --generated-key-input` 使用固定的计划色族自适应提取：允许同一计划色族内的渐变、亮暗变化和统一色漂移，不因输入四边未接近单一 RGB 就直接拒绝；每条非裁切边必须仍由计划色族稳定覆盖，主体有意裁切或贴边时必须用 `--allow-subject-touch-edge <top|right|bottom|left>` 明确声明。提取只删除与画布边界连通的计划色族和经审核确认的内部键色区域，自动延展干净主体 RGB 到软边并抑制键色残留；多色/不兼容边界、需要手动放宽参数、未声明的非键主体触边、主体内部损伤或最终深浅底/实际页面仍有可见色边时必须拒绝。禁止全局 HSV 删色、连续腐蚀或用主体内部深色像素覆盖边缘，并通过边缘与内部透明岛检查后才能进入 HTML。不得将通用自动抠图结果未经对照直接交付。
- 真实 Alpha 必须通过解码后的通道结构与 alpha extrema 判定：文件必须实际含 alpha 通道，且至少存在一个非完全不透明像素；PNG 扩展名、视觉棋盘格或“看起来像透明”都不是证据。失败时先记录“无 alpha / 背景烘焙 / 色键与主体重叠 / 边缘或内部透明岛异常”的具体拒绝原因，再按后续自动重试规则修正，不需要暂停等待用户授权。对已确认含真实 Alpha 的文件，alpha bounding box 触边本身不能直接判定主体被截断或触发重生成；必须先按视觉原子完整性检查触边连通分量，区分主体组成与孤立、极弱、未连接的离群像素。必需组成完整时，只有确认某个触边分量不属于该视觉原子后才允许确定性清理；禁止默认只保留最大连通分量，以免删除真实的分离装饰或部件。本判断不放宽计划色族安全检查、明确裁切边声明、主体完整性或最终可见残边门槛。
- 对同一已生成文件执行确定性的 alpha 蒙版修边、去除已选色键和质量检查，不计为新的图片生成调用；但它不能用于把意外白底、颜色与主体重叠或无法可靠分离的失败产物强行变成可交付资源。此时按质量失败处理，并遵守后续自动重试规则。
- 每个需要图片生成或重型图片编辑的视觉原子默认只执行 `1` 次高质量生成调用。首次调用必须直接使用最终级提示词、最终参考图、目标画幅、透明度要求和不变量，不得先生成低质量草稿、无依据候选或“试试看”版本；这一限制只减少同一视觉原子的重复调用，不是整页生成资源总数上限。不得为了把任务留在轻量/中等级、赶在首次综合预览前或控制调用总数，合并本应独立的视觉原子、把生成路由改成证据不足的裁切/抠图，或省略必要资源；不得降低模型、分辨率、输入保真度或输出质量。
- 使用支持 `generatedImage(result)` 的 `image-gen`/内置图片工具时，首次调用必须在同一次工具执行中正确返回并展示结果，同时记录工具提供的保存路径或 `output_hint`。调用已成功但界面未显示、包装代码未转发图片、路径未被打印或返回结构与预期不同，均不得判定为生成失败；先检查原始返回值和本次调用新产生的 `$CODEX_HOME/generated_images/` 文件，禁止为了补显示、补路径、取候选或修复调用方结果处理错误而再次生成同一资源。使用其他已有生图模型时，按该工具实际返回结构保存并展示结果，不强套 `generatedImage(result)` 或 `$CODEX_HOME/generated_images/` 路径约定，但仍须记录最终文件路径并执行同一套质量检查。
- 只有确认首次调用没有产生任何可用文件，或首次产物客观未通过 alpha、边缘裁切、有效分辨率、视觉原子完整性或固有文字/结构等质量硬门槛时，才允许自动执行针对性重试；图片生成重试不需要用户授权，也不得因此暂停任务。重试前先记录具体失败证据、额外耗时和拟修改项，并在下一次正常进度更新中简短告知用户后直接继续。每次重试只能修正已证实的失败原因，不得扩展候选、顺带改风格或为了避免继续失败而降低质量。相同资源连续两次仍未通过同一硬门槛时，停止该方法的重复调用，改用清单中下一个可靠方案；资源一旦在清单中确定为 `IMAGE`，所有 fallback 必须仍产出 `IMAGE`，生成、透明度或分辨率失败不得把它降级为 SVG/CSS/原生几何。若所有合规图片方案都已失败，则保留证据并报告阻塞，不再无上限生成或静默改变语义类型。HTML 完成前不设置图片生成审批门；整个流程唯一的强制用户审批点是完成内部源 HTML、双通道 Capture HTML、构图报告和最终截图后的“HTML 审批门”，该审批仅用于授权导入 Figma。
- 除 Logo、品牌字标和插画/图片内部的固有图案外，页面中所有承担导航、操作、状态或信息提示职责的 UI 图标必须调用 Icon Library，默认使用 Hugeicons（`@hugeicons/core-free-icons` / `@hugeicons/react` 或对应的 Hugeicons Figma Library）。禁止用 emoji、Unicode/文字字符、CSS 拼接形状、手写 SVG path、临时复制的第三方 SVG 或截图裁切来替代 UI 图标。HTML 中必须保留可追溯的库引用、图标名称和渲染入口（例如 `data-icon-library="Hugeicons" data-icon-name="ArrowLeft01Icon"`）。Figma 中沿用同一轮图标/组件检索，只有候选的描边/面性、轮廓、方向、笔画与颜色、外壳/底板、材质和状态均与参考图一致时，才导入目标文件已连接的发布组件；名称或语义相同不能代替视觉匹配。对录音、语音等明显定制且视觉权重高的复合控件，按“控件职责 + 状态”选择精确 Variant，并以完整组件 `Instance` 交付，不得退化为通用图标加近似底板。通过验收的发布图标命名为 `Icon/DesignSystem/<published-name>` 并记录 `componentKey`；没有视觉匹配的发布组件时，建立或复用 `Icon/Hugeicons/<name>` 主组件并以 `Instance` 放入页面。箭头、关闭、展开/收起等 UI 图标不得以普通 `Vector` 作为页面最终图层；Vector 只允许存在于图标主组件内部。若 Hugeicons 没有完全匹配的图标，选择最接近的库图标并记录映射，不得静默回退为自绘路径。
- 图标库前置检查是硬门槛：生成 HTML 前先确认 Hugeicons 包或 Figma Library 可用，并列出页面所需 UI 图标与库名。构建器遇到 Hugeicons 标记时，按“显式 `--hugeicons-dir` → 当前任务目录向上的既有包 → Skill 私有 `tooling/` 包”查找；三处都缺失时才通过 `scripts/bootstrap.mjs` 在 Skill 私有目录完成一次初始化，不改变已有任务的包来源，也不要求锁定团队统一版本。只有初始化实际失败时才停止并报告，且不得为了完成页面而使用自绘/内联 SVG。没有 Hugeicons 标记的页面不触发初始化。采集前必须扫描 HTML，除 Logo、品牌字标、插画内部固有图案、容器底板、渐变和其他非图标几何外，不得存在未标注库来源的 UI 图标 SVG；采集后必须抽查 Figma 图标节点名称/组件来源，确认每个 UI 图标仍可追溯到 Icon Library。
- 同一组 UI 图标必须统一来源版本、`viewBox`、渲染外框和描边缩放；HTML 与 Figma 不得仅因图标名称相同就复用几何不同的旧组件。现有组件的源尺寸、路径或描边与 HTML 库渲染结果不一致时，在既有一次 Figma 规范化中直接从同一库 SVG 建立正确尺寸的主组件并替换为 Instance，不新增候选板、截图或 Capture。
- 字重必须逐文本块以参考图的视觉证据为准；角色默认值只在证据不足时作为兜底，不得覆盖同倍率下清晰的笔画粗细和字面面积差异。灰色正文、说明文字等证据不足时使用 `400`，按钮/控件文字证据不足时使用 `500`，标题证据不明确时也优先 `500`；若现有综合截图显示某个正文块的 `400` 明显偏细，只比较该块同字体的 `400/500` 并局部修正，不把整页正文统一加粗。不得因为元素是标题、按钮，或使用了 `<strong>`/`<b>`，就自动设为 `600`/`700`。`600` 仅在参考图确实明显更粗时使用；`700` 默认禁用，只有用户明确指定或参考图与可用字体样本对比后有充分证据时才允许。
- HTML、浏览器预览与 Figma 必须使用同一字体族、同一来源/版本和真实存在的字重；禁止依赖浏览器 synthetic bold/伪粗体，也不能只依赖 Figma 面板显示的字体映射名称。Capture 后不得无条件重写字体：只有当前 Figma 执行环境已加载同一字体来源/版本，或代表文本重排后的度量指纹与 Capture 前 DOM 一致时，才批量解除 `font family/Font 1` 等临时字体变量/样式绑定并写入真实 `fontName.family/style`。若采集结果已与 DOM 一致、但无头环境不能证明字体同源，不得重新赋值 `characters`、`fontName` 或 `lineHeight` 触发替代字体重排。HTML 默认使用 `line-height: normal`，能够安全重排的 Figma Text 默认设为 `lineHeight=AUTO`，除非用户明确要求固定行高。
- 在执行字体映射和字体可用性硬门槛前，先完成“手写体证据判定”。只有参考图呈现明确的笔写特征（如笔画起收笔/连写、明显不规则的基线或字面比例、仿钢笔/毛笔的方向与力度变化），或用户/来源明确标注为手写体时，才判为手写体；单凭圆润、童趣、展示性、粗描边、软笔画端点或两端圆头不得判为手写体。圆体、圆润黑体和几何圆体一律属于非手写字体。证据不足时按非手写字体继续，不得触发 `YRDZST` 检查或阻断；用户对字体风格的明确纠正立即覆盖此前推断。
- 已确认字体映射是硬证据：若用户在当前对话、明确引用的历史任务或可验证交付中，已确认某段文案或同一视觉模板的真实 `family/style`，且当前参考图的字形风格没有变化，必须直接复用该映射，不得因新任务隔离、默认回退或再次主观判断而降级；这里只复用字体决策，不扫描、复制或覆盖历史任务资源。当前用户环境已确认：具有明确笔写特征的中文问候/引导文案使用 `YRDZST Regular`，不得写成 `PingFang SC`。若当前参考图明显改成另一字形，或用户明确纠正，则以当前证据为准。
- 中文和大号数字默认按以下映射执行，优先级为“用户对当前任务的明确指定 > 当前参考图的明确字形证据 > 同一文案/模板的已确认映射 > 下列固定兜底”：精确品牌标题“知识商城”使用 `Source Han Serif CN` 的 `Medium`；仅经手写体证据判定确认的中文使用 `YRDZST`；明确呈圆体/圆润黑体的中文选择浏览器与 Figma 两端共同可用、字形与字重最接近且不偏粗的圆体候选，没有合适圆体时直接使用 `PingFang SC`，不得因此阻断；纯数字或以数字为主体且字号大于 `24px` 的文本使用 `D-DIN`，货币符号、单位和中文应拆为独立文本并按各自字体规则处理；其余中文使用 `PingFang SC`。不得把 `D-DIN` 施加到整段混合中文。
- Capture 前在后台自动验证本次最终实际选用的字体族/字重。不得预检未被选用的 `YRDZST`。系统字体文件、浏览器 `document.fonts`、Figma 桌面端/字体面板、既有 Text 节点的真实 `fontName` 或用户明确说明“已安装/有这个字体”，任一可靠证据均可证明字体存在；无头 `use_figma` 的字体列表缺少本机字体或 `hasMissingFont=true` 不能单独推翻这些证据。字体有可靠可用证据时直接沿用，不再要求用户截图、确认或重复核对，也不要在 commentary/交付中展示字体探测过程。只有确认浏览器与用户实际 Figma 环境都没有目标字体、且没有相反证据时，才自动替换为两端共同可用、字形类别与字重最接近且不偏粗的字体：手写体匹配手写体，圆体匹配圆体，黑体匹配黑体，衬线体匹配衬线体；按字面宽度、笔画形态和换行稳定性选择，不得回退到无依据的 `700`。在内部清单记录最终映射；交付最多简短说明实际发生的替换，不展示核对流程，也不因可自动替换的缺字中断任务。
- 字体预检必须同时决定“字体映射”和“首次导入通道”。在既有综合浏览器预览中等待 `document.fonts.ready`，按每种最终 `family/style/weight` 只记录一个代表文本的 computed font 与 `getBoundingClientRect()` 宽高，作为轻量度量指纹；不得另开字体核对页或增加逐文本截图。通道选择不得只看字体族名称：若当前版本通过 `@font-face` 直接引用本任务版本目录内的字体文件（Inline 模式内嵌或 External 模式相对加载均可），且 `document.fonts.ready`、`document.fonts.check()`、代表文本 computed font 和度量指纹均通过，优先使用官方 Capture；同一字体文件校验值、同一加载方式已有官方成功记录时也直接复用官方通道。只有页面仅依赖 `local()`/系统安装字体、字体文件不能被隔离 profile 同源读取，或同一字体文件校验值与加载方式已有“官方导入错误、本机插件导入正确”的可靠记录时，才第一次就选择用户已授权的本机 Chrome/Figma 导入路径。历史失败只约束相同字体文件版本与加载条件，不得把 `YRDZST` 或其他字体族整体永久标记为官方通道不可用。用户已授权本 Skill 在命中本机字体隔离条件时使用现有插件，无需重复询问；不得安装新扩展、改变权限或访问无关标签。
- 字体与通道选择是 Capture 前不可跳过的硬门槛：在同一次综合预览中为每个可编辑文本块记录“文案/角色 → 预期 `family/style/weight` → 字体文件来源/校验值 → 证据 → 实际 DOM computed font → 导入通道”，实际 DOM 字体与预期映射不一致、字体文件未加载或度量指纹未记录时停止采集。`YRDZST` 本身不是强制插件条件；任务版本内字体文件通过上述加载门槛时走官方通道，仅依赖本机字体或同条件官方导入已有失败证据时走本机字体通道。该硬门槛复用现有综合页面打开与截图，普通字体页面以及已通过版本内字体验证的 `YRDZST` 页面都不新增字体专用页面或截图。
- 可控的文字排版数值默认使用整数且优先使用偶数字号：`font-size` 优先从相邻偶数候选中选择，字距以及文本层的 `x/y/width/height` 优先落在整数 CSS px/Figma px；行高默认保持 HTML `normal` / Figma `AUTO`。不得把高分辨率截图按比例机械换算出的 `17.5px`、`28.8px` 等小数直接带入 HTML 或 Figma。只有用户明确指定，或同画布对照证明奇数/小数值明显更接近参考图时才允许使用，并记录原因。
- 标签、按钮、胶囊和图标底板中的文字必须按可见底板边界居中，不得用目测 `top` 值近似。HTML 优先由容器 `flex/align-items/justify-content` 控制；Figma 在真实字体批量重排后按底板与 Text 的实际宽高重新计算中心位置，并合并进既有规范化批处理和最终综合截图，不增加单独验收步骤。
- Figma 交付前在后台执行“编辑态字体稳定性”检查：按每种实际 `fontName.family/style` 只抽查一个代表 Text。若当前 Figma 执行环境已加载同源字体，单一样式代表 Text 可重新赋值同一字体与文本并将结果与 Capture 前 DOM 度量指纹比较；混排 Text 按下一条的范围保护规则处理。通过后才在同一次批处理中重排该字体的全部 Text、设为自动行高并确认 `hasMissingFont=false`。若节点来自已选定的本机导入通道，或无头运行时无法加载已有可靠可用证据的本机字体，则只读比较字体名称、宽高、换行和基线，不得通过重新赋值来“测试”，也不得改字、重排或强行重组该 Text。确认字体确实不存在时先自动替换为近似字体，再完成同样检查。整个过程合并进既有一次字体审计，默认不向用户展示。
- Capture 代表 Text 与 DOM 度量指纹不符、但当前 Figma 执行环境能够可靠加载目标字体时，先在一次临时批处理中按每种实际 `family/style` 创建并删除一个全新、无绑定的 Text 候选，形成 `DOM → Capture Text → fresh Figma Text` 三阶段指纹。Fresh Text 必须使用真实字体并保持字形类别、字重、字符、显式换行和行数；单行自动宽文本允许采用 Figma 原生 Auto 的自然宽高，固定宽正文则必须保持原宽和换行并仅自动增长高度。若 fresh Text 正确而 Capture Text 仍保留旧几何，停止在旧节点上叠加修补，按 [references/figma-normalization.md](references/figma-normalization.md) 执行受控替换并由父容器吸收原生度量差。默认 `letterSpacing=0`；只有源设计本来存在非零字距或用户明确要求时才保留/设置相应字距，不得用字距补偿把 Figma Auto 文字强行压回浏览器盒子。
- `lineHeight=AUTO`、面板显示正确字体名和 `hasMissingFont=false` 不能单独证明编辑态稳定；Capture 仍可能保留浏览器文字盒几何。若 fresh Text 与 Capture Text 的自然宽高不同，不得给旧节点补固定行高、负字距或反复重设属性来维持旧盒子。应按 [references/figma-normalization.md](references/figma-normalization.md) 用全新原生 Text 替换受影响节点，保持 `textAutoResize`、真实字体、`lineHeight=AUTO` 和源设计实际字距；Auto Layout 父级保留原索引与 sizing，普通叠层父级按原文字盒的视觉锚点重新定位，并通过最终截图确认无裁切、重叠或明显视觉退化。
- 对混合字重、颜色或其他 range 样式的 Text，替换前必须完整保存 `getStyledTextSegments()` 的范围和样式，创建 fresh Text 后逐范围恢复。禁止在正式混排节点上用 `text.characters = text.characters`、整段重新赋值或整节点 `fontName/fills` 作为“双击测试”；该操作在部分 Figma 执行环境会把混排合并为首段样式。普通单一样式 Text 可用同内容回写验证几何稳定；混排 Text 只做范围、字体、Auto 行高、边界和截图审计，或在临时节点上测试并在同一调用内删除。
- 禁止通过父级或文本自身的 `transform: scale(...)`、非整数 `zoom`、小数 `rem`、百分比/无单位行高来缩放文字后采集；这些写法容易把整数样式转换成 Figma 小数。必须直接在最终标准画布上使用整数 `px` 设置文字，并通过字号、行高和容器尺寸本身完成匹配。
- 必须以最高优先级理解并还原界面视觉：逐一比对组件的结构、层级、尺寸比例、圆角、描边、材质、阴影、渐变、透明度、排版、间距、状态与可推断交互；明显渐变至少取样起点、终点和方向，不得用单色近似；最终截图同时检查切角/裁切、遮挡关系和前后层级，不得以“整体看起来相近”为由省略组件细节。
- 参考图不是可直接铺到页面上的合成素材。**只允许将不含 UI、IP、人物、装饰前景或文字的纯场景层作为背景资源**；绝不允许将整张参考图、包含前景的截图，或其大面积裁切，作为页面背景、遮罩或主视觉底图。允许从高分辨率参考图提取独立前景视觉原子，但提取结果必须通过分辨率、边缘和资源隔离检查。
- 必须将前景视觉逐项拆分为独立资源：IP/人物、画框、角色、书封面、礼物/活动贴纸、背景中的导航或设置元素、插画和其他装饰。每项都作为独立图层放入 HTML；简单 UI 几何和标准图标重建为原生形状或 SVG，完整 IP 与复杂视觉原子使用独立透明 PNG。优先使用用户提供的独立原始资源；只有合成截图时，简单硬边对象按“干净裁切 → 抠图/分割 → 修边 → 仅补全被遮挡区域”的顺序处理，复杂脆弱边缘对象按前述规则直接使用参考图生成/编辑。仅当源图缺失、遮挡严重、有效分辨率不足，或复杂边缘无法可靠分离时才重新生成，不能为了统一风格重画可干净复用的素材。禁止把包含背景或相邻 UI 的截图裁块直接交付。
- 资源拆分必须以“可独立替换的视觉原子”为边界，不得把一个完整物体的固有组成误拆成页面 UI。完整 IP/人物默认整体作为一张图片，不拆分头发、五官、身体、衣服、肢体、手持道具、固有光影等内部组成，即使其画风扁平也不自动改为 SVG。书籍、包装盒、海报、卡片插画、唱片封套、商品外观等也应作为一个完整 SVG 或图片资源；其封面印刷文字、Logo、图案、书脊、页芯、后封露边、厚度、高光和物体固有阴影属于该资源内部，不应另建 HTML/Figma 文本或形状层。只有用户明确要求编辑对象内部结构，或源文件本身已有可靠分层矢量时，才继续拆分。
- 复杂画框、剪纸/石材/手绘边框、复杂礼物、材质丰富的徽章、密集装饰插画等默认作为一张独立透明图片，不拆成大量 Vector。复杂性的证据包括：多个不规则部件、纹理或噪点、精细高光与阴影、材质边缘、密集路径，或用少量基础形状无法高保真表达。画框图片只承载画框本体；其内部的卡片、标题、正文、按钮和其他 UI 必须保持独立可编辑，不能与画框合成一张图。
- 位于复杂图片外部、承担页面信息层级，或需要动态更新、交互、数据绑定、本地化/无障碍读取的 UI 文本与控件必须拆成独立 DOM/Figma 层。例如礼物本体可是一张图片；其旁边或覆盖其上的促销标签若属于可变运营文案，则使用独立 Rectangle + Text，若明确是插画固定组成且不会更新，才允许并入礼物图片。
- 卡片缩略图、照片槽位和矩形内容插画的位图只承载媒体内容像素，不得烘焙卡片边框、圆角描边、阴影、选中态、文字、勾选/锁定图标、状态遮罩或相邻卡片内容。保留未破坏圆角的矩形源图；由唯一且有明确职责的卡片/媒体裁切容器承担 `overflow/clip`、圆角和裁切位置，由独立 Rectangle、Text 与 Icon Instance 承担边框和状态。隐藏媒体 `<img>` 时卡片外壳、文字与状态仍应存在；隐藏状态层时媒体内容不得改变。若参考图只显示源图局部，在资源清单和构图契约中记录可见裁切边界与焦点，禁止通过把多余 UI 裁进位图来碰位置。
- 图片格式与交互语义必须分别判断。纯装饰 IP、画框、礼物和插画默认不创建点击热区、Prototype 交互或仅为“可点击”而增加的外层 Frame；只有参考页面明确存在交互或用户明确要求时，才增加独立透明交互容器，图片本身仍保持一个不可拆的视觉资源。
- 用户提供的红框、箭头、圈选、批注文字等反馈标记默认只用于定位问题，不属于待还原设计；除非用户明确要求保留，不得生成进最终资源或页面。
- 透明 PNG 的布局尺寸和位置必须以 alpha 通道的非透明可见边界为准，不得以 PNG 文件画布、`<img>` CSS 外框或 Figma 图片节点外框代替可见主体边界。生成后必须测量 alpha bounding box、记录四周透明留白比例，并按参考图中的可见目标尺寸反算 `<img>` 的 CSS 尺寸和位置；若目标只应显示资源的一部分，还要检查 alpha 边界附近的离群像素/半透明像素，避免 HTML 缩小时看不见、Figma 重采样后重新露出。只有检测到此类裁切风险时，才在 HTML 与 Figma 使用一致的显式裁切 Frame/Mask，并记录其裁切职责。
- 纯背景也必须作为独立图片图层：在 HTML 中使用位于根画布首层、`z-index` 最低的 `<img>` 元素（如 `背景/纯场景背景`），其 `x/y` 为 `0/0`、尺寸严格等于根画布；背景资源本身也必须为目标宽高比且四边没有透明、深色蒙版或误留内边距。Figma 终检既核对背景节点尺寸，也核对导出图四边和四角的实际像素覆盖，不能只看到 `812 × 375` 就判定铺满。禁止将背景写为 `body`、根画布或任何 Frame 的 CSS `background-image`、渐变底图或 image fill。
- Figma 采集后，纯背景必须保留为根画布内最底层的独立图片节点，而不是根 Frame 的填充。若采集结果将背景变成 Frame fill、复合截图或与前景合并，必须调整 HTML 为独立 `<img>` 背景层后重新采集。
- 位图必须以一个直接图片图层交付：背景、画框、人物、书籍及其他 PNG/JPG 各自直接作为所属页面画板/容器的子节点，外面不得再套仅用于“承载图片”的 Frame、Group、Mask 或同尺寸包装层。Figma 底层可将这个直接图片图层表示为一个叶子 Rectangle + `IMAGE` fill；该 Rectangle 本身就是图片图层，不是“Rectangle 容器 + 内部图片”。禁止交付 `Frame → 图片图层`，也禁止交付无子节点、无容器职责、仅有 `IMAGE` fill 的叶子 Frame。
- 只有图片确实需要裁切/蒙版、Auto Layout、滚动、响应式约束、独立交互命中区或原型行为时，才允许存在外层 Frame/Mask；必须记录具体职责。仅用于定位、缩放、命名、分组或承载图片不构成保留外层节点的理由。
- 背景以上的前景资源默认必须独立，但不默认全部矢量化。纯色/渐变横条、地台、砖块、卡片底板、按钮底板、色带、圆点等简单图形必须转换为 Rectangle、Ellipse、Vector 或由这些节点组成的 Group；完整 IP 和已判定为复杂视觉原子的对象则直接保留为独立图片图层。
- 规则的轴对齐矩形或圆角矩形（包括卡片、按钮、面板、标签、输入框、横条和平台底板）默认仍以 Figma 原生 `Rectangle` 为目标，通过 `cornerRadius` 或四角独立半径保留可编辑圆角。仅允许一个不改变 HTML 生成策略的导入验收例外：现有 HTML 按原有视觉与交互要求使用内联 SVG 后，Figma 导入器稳定产生“无 fill/stroke/effect、无裁切/蒙版/布局/交互职责的透明 SVG 根 Frame → 唯一可见 Vector/Shape”，且全部外观均在子节点上、子节点可在 Figma 属性面板直接编辑填充/描边/圆角，并已通过视觉与交互回归时，可以原样验收，不要求为图层纯度删除透明 Frame 或重建为 Rectangle。该例外只修正 Figma 导入结果的判定，不得用于改变 CSS/SVG 选型、DOM 结构、现有 HTML、构建器或预检脚本，也不得推广到有外观的 Frame、多子节点 SVG、UI 图标或不满足上述条件的结构；例外之外，只有轮廓确实不规则、非矩形、含路径切角/凹口，或无法用 Rectangle 四角半径表达时才允许使用 Vector，规则圆角矩形底板的 Vector 数量仍必须为 `0`。
- 全宽元素不自动等于背景。只有同时满足“位于最底层、覆盖或承载整个场景、移除后只剩前景 UI/资源、内部不含 UI/IP/人物/文字”的纯场景层才允许作为背景位图；位于背景之上且仅占局部区域的地面、平台、色带、阴影和装饰即使横跨整屏，也属于前景资源，再根据其几何复杂度和内部编辑价值选择矢量或图片。
- Frame 只能用于真实容器职责：Auto Layout、裁切、滚动、响应式约束、交互命中区、原型行为或必须承载子节点的布局边界。仅有 fill、圆角、阴影、描边、渐变或纯装饰子节点，不构成保留 Frame 的理由；纯视觉集合使用 Group。
- 新任务默认使用 HTML-first Auto Layout V2：在编码前把真实容器判定为 `row / column / wrap / overlay / viewport`，并记录横纵向 `fixed / hug / fill`；`row / column / wrap` 必须用 Flex、直接子节点、`gap` 和 `padding` 实现，只有真实重叠构图、裁切、滚动和交互边界使用 `overlay` 或普通 Frame。完整规则见 [references/html-first-auto-layout.md](references/html-first-auto-layout.md)。
- V2 新任务必须在 `#canvas` 写入 `data-figma-layout-version="2"` 并复制使用 `assets/semantic-layout.css`；每个布局容器写入 `data-figma-layout`、`data-figma-width` 和 `data-figma-height`。复制后的 CSS 必须位于当前任务独立版本目录，禁止直接链接 Skill 中的共享文件。
- 没有 V2 标记的历史 HTML 和当前任务旧版本保持原流程；连续修改时不得为了套用新规则自动迁移、重排或覆盖旧页面，除非用户明确要求升级该页面结构。
- 交付前必须审计目标画板内所有位于背景以上的节点。除按视觉原子规则保留的独立图片和前述严格受限的透明 SVG 根 Frame 外，“仅用于绘制外观的 Frame”和“无容器职责的叶子 Frame”数量必须为 `0`；不能以“仍然可缩放”替代正确的节点语义。
- 采集前必须验证资源分层：背景、每个前景 SVG/图片、文本、图标、卡片和交互控件均可单独隐藏或替换；若关闭任一前景资源仍能看到它，说明错误复用了合成截图，必须先修正。
- Figma MCP 操作前必须先加载并遵守 `figma-use` skill；每次调用 `use_figma` 前都要满足其前置要求。
- 官方 Capture 通道必须使用长期保留、仅供 Figma HTML Capture 使用的独立 Chrome 用户数据目录和浏览器实例；同一用户后续任务默认复用该专用 profile。

- 通过字体预检的正常页面默认使用 Figma 官方 `capture.js` + 一次性 Capture ID，不依赖 Chrome 扩展，也不得要求用户登录 Figma 网页版。命中“本机字体隔离”条件时，将已授权的本机 Chrome/Figma 插件作为首次导入通道，而不是先走一次已知不稳定的官方通道。

- 安装稳定预览服务属于一次性持久环境修改，只有用户明确授权时才可执行 `preview-service.mjs install`。普通图片任务只能检查身份、复用服务、注册当前版本和核对磁盘/HTTP 字节，不得静默安装、修改固定端口或连接身份不明的监听进程。服务未安装、不可恢复、身份不符或端口冲突时，保留全部任务产物并阻断“稳定预览”交付；不得把随终端结束的临时 URL 称为稳定预览。
- 不要只把整张截图作为一个图片导入；HTML 应尽量保留文本、按钮、卡片和主要元素的独立 DOM 层，以提高 Figma 可编辑性。

## Figma 目标策略

本节只决定审批通过后的目标位置。HTML 审批通过前可记录用户给出的链接、`fileKey/nodeId` 或默认 plan，但不得新建文件、创建 Capture ID、调用插件导入或执行 Figma 写操作；目标可访问性和写权限最迟在审批通过后、首次写入前确认。

- **用户没有提供 Figma 链接**：在创建文件前告知用户将新建 Figma 文件。先读取当前已认证账号的 `whoami`/plan 结果；只有结果中存在“猿辅导体验设计”plan（`planKey: team::1634053011581078191`）且当前账号具备写权限时，才将其视为团队成员并优先在该 plan 的 Drafts（草稿）中新建设计文件。该 plan 不存在或不可写时，不尝试访问、不触发一次预期会失败的创建，也不要求外部用户选择你方团队；直接使用 `whoami` 返回的当前账号默认/个人可写 plan，在对方自己的 Drafts 中创建。若工具没有明确标记默认 plan，则使用当前账号返回列表中的第一个可写 plan；完全没有可写 plan 时才暂停并说明登录或权限问题。任何分支都不传 `projectId`，不得创建到团队项目或其他文件夹。团队 plan 名称与 ID 只用于内部路由；对未命中该 plan 的账号，不在进度、错误或交付信息中展示它们，只称“你的 Drafts”。加载并遵守 `figma-create-new-file` skill 创建文件，再使用新文件链接完成采集，最后返回文件链接和节点链接。

## Figma 图层语义与前景资源规则

先按视觉职责确定最终节点类型，不要按 HTML 标签名或 Capture 的默认结果倒推设计语义：

| 视觉职责 | 最终 Figma 节点 | 处理要求 |
| --- | --- | --- |
| 纯场景背景 | 直接图片图层（叶子 Rectangle + IMAGE fill） | 直接作为根画板最底层子节点；外面不套 Frame，不与任何前景合成 |
| 矩形、圆角矩形、横条、平台、砖块、色带、按钮/卡片底板 | Rectangle | 保留 fill、渐变、圆角、描边和阴影；不要保留为纯样式 Frame |
| 圆点、圆形、椭圆 | Ellipse | 不要用圆角 Frame 模拟 |
| 导航、操作、状态与信息提示 UI 图标（含箭头、关闭、展开/收起） | Instance | 优先导入已发布设计系统图标组件；否则建立/复用 Hugeicons 主组件并实例化。页面最终图标节点不得是普通 Vector |
| 简单植物或可由少量路径表达的非 UI 不规则装饰 | Vector | 使用 SVG path 或 Figma Vector；同色路径可合并，不同 fill 可保留为多个 Vector |
| 可编辑文案 | Text | 保留真实字体、字重、字号和行高；不要轮廓化 |
| 只需一起移动的纯视觉节点 | Group | Group 内使用 Rectangle/Ellipse/Vector/Text；不要为组织图层创建 Frame |
| 单轴排列或换行布局容器 | Auto Layout Frame | 行、列、卡片内容、统计行、进度行和标签组使用横向/纵向 Auto Layout 或 Wrap；可见底板保持独立 Shape |
| 叠层、裁切、滚动、响应式边界或交互容器 | Frame | 仅在真实重叠、裁切、滚动或交互职责需要时保留；不得把普通排列继续留为 `layoutMode=NONE` |
| 完整 IP/人物、复杂画框/剪纸边框、复杂礼物、书籍/商品外观、照片或材质丰富的前景 | 直接图片图层（叶子 Rectangle + IMAGE fill） | 一个视觉原子对应一个独立图片图层；不拆内部结构，外面不套包装 Frame，并记录图片边界与交互判断 |

执行以下判断：

1. 先锁定唯一的纯场景背景层，再把其上所有独立可见对象列入“前景节点清单”；不要因对象全宽、面积大或靠近画布底部就把它归入背景。
2. 对每个前景对象先回答：它是否是一个完整、可识别且通常整体替换的视觉原子？用户是否需要编辑其内部结构？它是否包含复杂纹理、材质、阴影或密集部件？完整 IP 默认直接判定为一个图片视觉原子；复杂画框、礼物和装饰在内部无编辑需求时也判定为图片。只有简单几何、标准图标、动态 UI 和确有内部编辑价值的对象才使用 Rectangle、Ellipse、Vector、Text 或 Group。
3. 将按钮、卡片、木牌等拆成“透明布局/交互容器 + 可见底板 Rectangle + Text/图标”；内容存在行列排列时容器使用 Auto Layout，真实叠层或纯交互命中时才保留普通 Frame。容器不承担绘制外观；只有底板轮廓确实不规则且不能用 Rectangle 四角半径表达时才改用 Vector。
4. 将纯视觉组合（例如仙人掌主体和高光、六块砖）组织为 Group；有不规则轮廓时使用 Vector，有规则几何时优先使用 Rectangle/Ellipse，避免不必要的 Flatten。
5. 不把“扁平风格”当作 IP、人物或完整插画必须矢量化的证据。完整 IP 默认使用一张透明图片；只有用户明确要求编辑其内部结构，且使用 SVG 能保持视觉质量和合理图层数量时，才改用 SVG。复杂画框、复杂礼物和材质装饰同理。
6. 再单独判断交互：视觉原子是否可编辑、是否为图片，与它是否可点击没有必然关系。纯装饰对象默认没有交互；原页面明确可点击时，在图片外建立有明确命中职责的透明 Frame，但不得为了组织、定位或命名创建包装 Frame。
7. 对每个位图执行“单层检查”：从页面画板向下应直接命中一个带 `IMAGE` fill 的叶子图片图层，不得先经过仅包裹该图片的同尺寸 Frame/Group。画框内部的 UI、背景上方的人物等均与相应图片图层保持同级，不能塞进图片包装层。
8. 对每个真实容器执行布局语义判断：能以一条主轴或换行排列的内容标为 `row / column / wrap`；只有背景、人物、标题装饰、角标、进度条轨道与填充等确需重叠的结构标为 `overlay`。不要因参考图是固定尺寸就把流式内容改成绝对定位。

优先从源头减少 Frame：

- 不要用 `div`、`span` 和 `::before`/`::after` 拼接需要在 Figma 中矢量编辑的前景图形；官方 HTML-to-Design 会把 CSS 盒模型采集为 Frame。
- 对需要保留为位图的背景、画框、人物和复杂资源，直接使用定位后的 `<img>`；不要为 `<img>` 增加只负责尺寸、定位、命名或图片承载的包装 `div`。若真实交互/裁切必须使用容器，应在资源清单中标记，并在 Capture 后保留对应职责。
- 对规则矩形/圆角矩形使用独立可见底板层，并标注 `data-figma-node-type="RECTANGLE"`、`data-corner-radius="<n>"`（或四角值）和语义名称；HTML 继续按既有规则用 CSS 或 SVG 保持视觉。Capture 后默认按该语义重建为原生 Figma Rectangle；若结果完整满足前述透明 SVG 根 Frame 例外，则直接验收，不执行删除包装层或 Rectangle 重建。圆形/椭圆同理标注为 `ELLIPSE`；只有确实不规则的简单轮廓才以 `<path>`/Vector 交付。对交互容器使用透明 DOM 容器，底板与容器分离。不要用内联 SVG 拆绘完整 IP 或复杂装饰来追求无实际价值的内部可编辑性。
- HTML 使用 Hugeicons 的真实 SVG 渲染结果且不栅格化；Figma 归一化阶段将每个 UI 图标替换为发布设计系统组件或 Hugeicons 主组件的 `Instance`，普通 Vector 只保留在主组件内部。
- Capture 完成后仍必须做节点语义审计，并对不满足目标语义的节点执行归一化；不能假设 SVG 或 CSS 会自动得到期望的顶层类型。完整满足前述透明 SVG 根 Frame 例外的节点已经通过语义审计，不为消除透明包装而单独归一化。

加载并遵守 `figma-use` 后，只处理本次 Capture 返回的目标根节点。标准成功路径使用一次批量写操作完成归一化；只有节点数量超过工具限制、操作存在依赖顺序或发生错误时才拆成小批次：

1. 先记录 Capture 返回的最终根节点 ID，直接检查该子树，禁止为定位新结果而扫描整个大型 Figma 文件。
2. 将无子节点、无容器职责、仅包含视觉样式的 Frame 重建为 Rectangle/Ellipse；若它仅有 `IMAGE` fill，则重建为同位置、同尺寸、同图片 fill 的直接叶子 Rectangle 图片图层。若结构为“包装 Frame 只含一个同尺寸图片子节点”，把图片子节点提升到包装 Frame 的父级并保留绝对位置、尺寸、透明度、旋转与约束，然后删除包装 Frame。将其他嵌套 CSS 图形按其几何重建为 Vector 或原生形状。
3. 不把 `flatten()` 作为嵌套 Frame 的首选转换方式；它可能失败或降低编辑性。优先用 `createRectangle()`、`createEllipse()`、`createVector()`、`vectorPaths` 或 SVG 导入。SVG 导入若产生包装 Frame，先按前述透明 SVG 根 Frame 例外审计：完整满足条件时原样保留；否则保留内部 Vector/Shape，移除仅用于导入的空包装层。
4. 保留 Text 节点，不将文案转轮廓。移动或重组含文字的节点前先加载其实际字体。
5. 将 V2 的 `row / column / wrap` 容器规范化为 Auto Layout 前，先记录容器和直接子节点的宽高、顺序与相对位置；先把底板、标题装饰和其他叠层子节点设为绝对定位，再设置方向、Wrap、间距、内边距和 Fixed/Hug/Fill，最后检查尺寸、文本换行和子节点越界。不得机械地把所有 Frame 改成 Auto Layout。
6. 在 Auto Layout 容器内新增绝对装饰层时，设置正确的绝对定位；若容器本来不需要 Auto Layout，则显式恢复 `layoutMode = "NONE"` 和原始尺寸，防止插入形状后被撑大。
7. 每个写操作返回全部创建、修改和删除的节点 ID；标准路径在整批归一化后执行一次结构审计和一次截图。拆批或遇到错误时才检查中间状态，先确认是否存在部分修改，再清理或续作，不盲目重试。

## 效率优先执行路径

不降低尺寸、视觉、字体、图标和图层语义验收标准，但将正常任务压缩为“一个清单、一次预检、一次 Capture、一次批量规范化、一次终检”：

1. 只建立一份“资源—DOM—交互—构图契约—最终 Figma 节点类型”清单，后续资源生成、HTML 标注、Figma 归一化和交付审计复用同一份清单，不为每个阶段重复整理。`composition-contract.json` 是其中可机检的几何/数量子集，不另做一份互相冲突的记录。
2. 对边缘稳定、可可靠提取的视觉原子按以下成本从低到高选择素材方案：`用户提供的独立原始资源 → 当前高分辨率参考图中的干净原子裁切 → 抠图/分割并修边 → 局部修补或补全遮挡 → 全新生成`。该顺序不适用于只有合成截图、且包含头发、手指、浅色/白色高光、发光道具、半透明材质或复杂镂空的完整 IP、人物和复杂画框；这类对象直接进入参考图生成/编辑，并按工具能力在首次调用选择真实 alpha，或使用与主体色域差异最大的安全高饱和纯色色键；浅绿、白色或发光主体默认使用已有成功记录的纯洋红 `#FF00FF`，不用最终落点背景决定色键优先级。卡片缩略图、照片和矩形插画只要内容边界完整、没有烘焙边框/文字/状态 UI、没有相邻 UI/背景且最低有效倍率达到 `1.5×`，就直接裁切复用；达到 `2×` 为首选，`1.5×–<2×` 记录实测倍率并继续 `100%`/`200%` 检查，不得为统一风格而无依据重新生成。不得扫描、猜测或复用其他历史任务目录；唯一例外是 [resource-routing.md](references/resource-routing.md) 规定的“精确参考图 SHA-256 + 已审批清单”语义决策复用，且只复用资源分类，不复用历史素材或页面文件。
3. 设置“单原子重复调用门禁”：先完成全部视觉原子的来源分类，再决定时间等级；不得先设整页生成数量上限再反向压缩资源路由。每个需要生成或重型编辑的独立视觉原子只取 1 个主结果，独立任务在工具可靠支持时并行执行。若清单证明有 3 个以上资源只能全新生成，立即判为复杂任务并报告 60–90 分钟等级，然后继续生成所有必要视觉原子；不得为了维持轻量/中等级而改成证据不足的裁切、抠图或 CSS 近似。只有 alpha、边缘裁切、分辨率、视觉原子完整性或固有文字/结构明显不合格时，才允许在首次综合预览前针对同一原子重试；比例、位置、大小和一般风格差异先进入完整 HTML，通过综合截图统一判断。
4. 初始资源完成后立即建立最终标准画布上的最小完整 HTML：放入背景、全部主要视觉原子、文本、简单形状和图标入口，然后先完成预检与一次综合截图；不得在尚未看到整体页面时连续优化单个资源。综合截图后只修正有明确视觉证据的问题，已通过 alpha/完整性检查且在整体中匹配的资源不得重复生成。
5. 延迟加载与当前阶段无关的重型上下文：本地 HTML 通过首次综合预览、且目标 Figma 文件或新建文件所属 plan 已确定前，不预加载 `figma-use`、`figma-generate-design`、Plugin API 索引、Gotchas 或其他仅供 Figma 写入/归一化使用的详细资料；只在即将调用相应 Figma 工具前按其技能要求完整加载。若不存在已记录且仍可写的默认 plan，账号又存在多个 plan，应在任务开始阶段尽早请求选择；等待回复期间可继续本地资源与 HTML，不得提前展开 Figma 端工作。
6. 内部源 HTML 完成后先做开发预检，再以 Inline 模式构建唯一 `*-capture.html` 并读取 `officialPayloadRisk`；有风险时在审批前重建为 External 模式。Inline 文件同时通过 `preflight_html.py --offline` 与 HTTP 模式预检；External 文件通过 HTTP 模式预检和版本目录依赖/哈希闭包检查。一次检查资源分类、复用证据、参考图哈希、DOM 资源节点类型、所选资产模式依赖、双通道条件加载器、背景图层标记、UI 图标溯源、字体声明、自动行高、字号、字重和缩放风险。V2 页面同时检查布局版本、布局语义、模板类、Fixed/Hug/Fill 和图标固定尺寸，并在缺少 schema v3 清单或契约参数时直接失败。修复其中的 error 后，只对唯一 Capture HTML 的稳定 HTTP URL 完成目标尺寸综合浏览器截图，并运行 `node scripts/check_composition.mjs <URL> <composition-contract.json> --output <report.json>` 检查真实 DOM 数量、锚点、边界、比例和层级；只有 Inline 模式且环境允许时再以 `file://` 检查同一文件，不创建第二份 HTML。任何 error 都必须先修正。复用同一次页面加载等待 `document.fonts.ready`、核对字体、记录代表 DOM 度量指纹，并检查背景四边、渐变、裁切和前后层级；不得以静态预检或构图脚本单独通过代替参考图视觉判断。
7. 输出隔离默认通过唯一任务/版本路径、依赖清单及校验值验证；只有检测到共享可变资源、可变路由或依赖越出当前版本目录时，才额外打开上一版本 URL 做回归检查。
8. 按标准工作流中的“HTML 审批门”交付当前 Capture HTML 的一个稳定预览链接、一张当前版本的最终预览图、目标尺寸和简短校验结论并暂停；详细报告留作内部证据，除非用户明确索要。没有绑定当前文件指纹的有效审批时，不得开始任何 Figma 导入或写入；用户提出修改后继续原地优化当前 HTML，重新完成第 `6–8` 步。
9. 审批有效且当前文件指纹未变化时，默认只执行一次由字体预检选定的首次导入：普通字体页面，以及字体文件位于当前任务版本目录、通过 `@font-face` 的 Inline 或 External 加载并完成 DOM 字体/度量验证的页面，创建并提交一次官方 Capture；仅依赖本机安装字体，或相同字体文件校验值与加载方式已有“官方错误、本机正确”记录的页面，直接执行一次本机插件导入，不先创建 Capture ID。不得因字体族名称是 `YRDZST` 就自动改走插件。体积风险只改变官方 HTTP Capture 的资源传输方式，不改变导入通道。图标命名、Frame/Group 清理、规则圆角 Vector 转 Rectangle、背景图片提升等 Figma 端语义问题直接在已导入目标子树修复；字体只有通过同源/度量门槛才允许重排。只有 HTML 布局、资源内容、字体加载、采集尺寸或导入后代表文本的字形/宽度/换行本身错误时才重新导入。
10. 导入完成后固定为四步：读取一次目标子树与必要字体/样式信息；执行一次批量规范化；执行一次结构/字体审计；执行一次最终截图。首次读取应一次取得节点类型计数、图片叶子、Frame 职责、代表文本度量和 Auto Layout 越界；只有出现字体指纹不一致时才在一次临时批处理中追加 fresh Text 候选，并在同一调用内删除候选。批量规范化必须跳过不能由当前执行环境安全重排的本机字体 Text，并按 [references/figma-normalization.md](references/figma-normalization.md) 的确定性顺序执行。最终截图同时验收高视觉权重控件和图标的描边/面性、颜色、外壳与状态，以及各文本块的实际字重；普通图标和正常透明图片不另建候选板或额外截图。只有审计失败、截图与参考图明显不一致，或透明边缘出现底色/光晕嫌疑时才追加局部读取和修复。除非用户明确要求，不创建候选页、组件展示板、额外设计系统、额外交互演示或与当前页面无关的规范资产。
11. 在资源生成、HTML/预览、用户审批等待、Capture 等待、Figma 规范化与终检各阶段开始和结束时记录墙钟时间；用户审批等待单独记录，不计入实际执行耗时。若同一执行阶段超过 10 分钟且没有产生新的可检查产物，立即停止该阶段内的候选扩展或无证据微调，保留已有正确产物并推进到最近的综合预览/审计点；不得因此跳过或降低最终视觉、字体、图标、图层语义与尺寸验收。交付时仅报告实际存在的瓶颈，避免以后凭感觉重复优化非瓶颈步骤。

## 标准工作流

### 1. 分析参考图

读取图片尺寸并计算宽高比，先按“用户指定具体尺寸或设备类型/方向（Pad/平板、手机横屏、手机竖屏） > 等比例标准画布 > 最接近的标准宽高比 > 画面形态推断”确定画布规格；用户明确指定设备类型/方向但未给具体尺寸时，分别采用 Pad `1024 × 640`、手机横屏 `812 × 375`、手机竖屏 `375 × 812`，不得因参考图比例更接近另一标准而改判。记录计算结果和选择依据后再拆解页面。以组件级精度拆解纯背景、IP/人物、画框、导航、主视觉、卡片、弹窗、按钮、图片、图标、文字和装饰层；为每一项记录边界、叠放顺序、相对比例、颜色、透明度、圆角、材质、阴影、描边、间距、字体族、实际字重、字体大小、行高、字距、默认/悬停/点击状态及可推断交互。先产出“资源—DOM—交互—最终 Figma 节点类型”对应清单，并逐项标为 `背景图片 / 完整视觉原子图片 / 简单前景矢量 / Text / Auto Layout 容器 / 叠层或裁切 Frame`，再开始生成或编码；不得以局部像素硬编码或整图覆盖替代结构化还原。

随后按 [references/composition-fidelity.md](references/composition-fidelity.md) 建立 `composition-contract.json`。固定画布页面至少覆盖主面板、角落人物/IP、主要画框/卡片、重复主体和高视觉权重不规则形状；记录目标画布坐标而不是原始高分辨率截图坐标。若宽高比发生变化，先写明纯背景如何延展/裁切、每个主体如何保持比例与锚点，再生成资源。

建立文字样式表并逐类取样比对，每个文本块必须记录预期 `family/style/weight`、判断证据和导入通道。先复用同一文案/模板已经由用户确认且当前字形未改变的字体映射，再执行当前参考图的手写体证据判定：品牌标题“知识商城”=`Source Han Serif CN Medium`；确认的手写风格中文=`YRDZST`；圆体/圆润黑体按非手写字体选择两端共同可用的最接近圆体；字号大于 `24px` 的纯数字/数字主体=`D-DIN`；其余中文=`PingFang SC`。不得因圆润、童趣、展示性或两端圆头将标题判成手写体；但具有明确笔写起收笔、字面比例变化或不规则基线的问候/引导文案不得回退为苹方。再处理用户对当前任务的覆盖和其他特殊字体。不要根据“标题/按钮”名称猜测粗细。默认基线为：正文/辅助说明 `400`，按钮/控件/标签 `500`，证据不明确的标题 `500`。如认为需要 `600` 或 `700`，必须先用同一字体族的 `400/500/600/700` 样本截图对照参考图，记录选择依据；无法确认时选择较轻的一档。参考图若来自高分辨率缩放，还要区分抗锯齿、描边、发光和截图缩放造成的“视觉变粗”，不能把这些效果误判成更高字重。

文字样式表中的字号优先生成相邻偶数候选，字距和文本框几何值生成整数候选。例如比例换算得到字号 `17.5` 时，先比较 `16` 和 `18`，仅当奇数值确实更接近时再使用 `17`；不要直接使用 `17.5`。位置和文本框尺寸同理。默认字距为整数 `0px`，默认行高为 HTML `normal` / Figma `AUTO`；仅当用户明确要求固定行高时才设置整数 `px`。

拆分前先执行“视觉原子判定”：判断文字、图案或结构是页面 UI，还是物体本身不可分割的固定视觉。遵循“可独立替换，但编辑粒度停在视觉原子”的原则：完整 IP 建立 `角色本体/服饰/表情/道具/固有光影` 内部完整性清单并由一张图片承载；复杂画框只将框体本身作为图片，框内 UI 另行拆分；复杂礼物由一张图片承载，外部动态促销标签另行拆分。对书籍等物体建立 `前封/封面印刷文字/封面插画/书脊/页芯/后封露边/厚度与材质` 清单。批注箭头只用于确定需要检查的区域。

同时按 [references/resource-routing.md](references/resource-routing.md) 写入 `resource-manifest.json` schema v3，并在每个高视觉权重对象的构图契约项中写入对应 `resourceId`。命中不规则固有部件、纹理/噪点、材质边缘、精细高光阴影、半透明/发光、密集路径或完整可识别插画任一证据时，不得把完整视觉原子标成 `simple-decoration`。只有用户明确要求内部编辑，或当前任务存在可靠分层矢量源文件时才可记录路由例外。资源清单完成后立即运行 `scripts/preflight_resource_plan.py`；通过前不得生成素材或编写 HTML。

### 2. 生成视觉资源

先建立资源分层清单，至少包含：纯场景背景、IP/人物、画框、各张内容插画/书封面、活动贴纸、独立装饰物和图标。为每项记录 `来源方式 / 最终显示尺寸 / 源有效像素尺寸 / 是否需要 alpha / 处理方法 / 预计耗时`，并先完成时间等级判断。只可将不含任何前景元素的纯场景层作为背景；若原图背景与前景已合成，优先对原图做前景移除和局部修补，不能直接使用整张参考图。纯背景文件也应作为单独的图片资源记录，供 HTML `<img>` 图层使用。对每个背景以上的资源同时指定目标格式和理由：简单几何、标准图标、动态 UI 和需要内部编辑的简单装饰使用 SVG/原生形状；完整 IP、复杂画框、复杂礼物、照片、复杂纹理和无需编辑内部结构的完整物体使用透明 PNG。

先从参考图提取可直接利用的高质量像素：矩形图片内容在边界完整且没有 UI 覆盖时直接无损裁切；非矩形主体只有在轮廓清晰、硬边、背景可明确区分且不含脆弱边缘特征时才优先抠图/分割并修边；只有被遮挡或超出截图的局部才做 inpaint/outpaint 补全。不得为了“重新生成得更统一”而重画可干净裁切或可靠分离的卡片图、人物或装饰。对于无法可靠分离的完整 IP、人物和复杂画框，参考图本身即使清晰，也应直接调用图片生成/编辑取得完整独立资源，而不是先尝试通用抠图；首次调用按已验证的透明能力选择真实 alpha，或选择与主体色域差异最大且不进入主体边缘、高光、发光及半透明区域的高饱和纯色色键。浅绿、白色或发光主体默认使用已有成功记录的纯洋红 `#FF00FF`；最终落点背景只在合成 QA 中检查，不参与色键优先级。

对完整 IP/人物默认生成或使用一张透明 PNG，不因画风扁平而拆成 SVG；对剪纸、石材、手绘等复杂画框以及复杂礼物、材质徽章和密集装饰同样优先使用透明 PNG。对可以用少量基础路径高保真表达、且确有内部编辑价值的简单装饰才使用 SVG。生成提示词或资源结构清单必须列全视觉原子的内部组成，不能只描述最显眼的正面图案；例如书籍至少核对封面文字与插画、书脊、页芯、后封露边、厚度和边缘材质。检查每个 SVG/PNG 的边缘裁切、画布留白、内部结构完整性和画风一致性；PNG 额外检查 alpha 通道和分辨率。标准 UI 图标必须使用 Hugeicons。

每个新透明资源一落盘就立即运行 `scripts/measure_alpha_bbox.py <asset.png>`，并在深色、浅色两种纯色底上做一次视觉检查；不要等所有素材完成后再检查。若资源来自预先选定的安全纯色色键，先按 [references/alpha-extraction.md](references/alpha-extraction.md) 运行确定性转换和 QA，再测量最终 Alpha 边界。同时保留抠图/分割前文件，导出或查看 alpha 黑白蒙版/透明区域热力图，扫描主体内部被不透明像素包围或近似包围的透明连通区域。把每个内部透明区域与抠图前文件、参考图和视觉原子内部清单逐项对照：只有来源中真实存在的镂空才允许保留；浅色、白色、高光、发光区域以及人物的手指、头发、服饰和手持道具不得因颜色接近背景而被误删。若没有真实 alpha、出现烘焙棋盘格/底色、主体被截断、边缘明显污染或新增内部透明缺口，立即拒绝该结果并局部修复蒙版，禁止继续进入 HTML 后才返工。alpha bounding box、文件外框和深浅底缩略图均不能单独证明主体内部完整。通过后记录文件画布尺寸、alpha 可见边界、内部透明区域判定、可见宽高与四边透明留白。布局时先从参考图量取主体的可见目标边界 `(target_x, target_y, target_w, target_h)`，再按下式反算完整图片外框，不得直接把 `(target_w, target_h)` 当作 `<img>` 尺寸：

```text
scale_x = target_w / alpha_visible_width
scale_y = target_h / alpha_visible_height
img_width = source_width * scale_x
img_height = source_height * scale_y
img_left = target_x - alpha_bbox_left * scale_x
img_top = target_y - alpha_bbox_top * scale_y
```

保持比例的资源优先使用同一缩放值；若参考图与生成资源的可见宽高比不同，先选择视觉主轴匹配并检查另一轴误差，必要时重新生成或裁整透明画布，不得无依据地拉伸变形。

### 3. 实现 HTML

先判断任务边界并锁定当前交付路径：新对话/新任务中重新上传或指定参考图片时创建全新的 HTML 项目；同一对话/任务中的连续反馈直接修改当前 HTML，不另建版本：

- 新任务从参考图文件名或页面用途生成安全的 `<source-slug>`，追加时间戳与随机/任务短 ID 创建任务目录；不要读取其他对话或任意历史目录来选择、复用或清理输出。首次生成写入 `v001/<source-slug>-v001.html` 和 `v001/assets/`。若当前对话明确提供了已审批历史清单，或存在按精确参考图 SHA-256 建立的可信决策索引，只允许按 [references/resource-routing.md](references/resource-routing.md) 复用资源分类证据，不得读取或复制历史 HTML/CSS/图片。
- 当前任务收到修改反馈时，先核对正在预览/交付的 HTML 绝对路径、标题与任务标识，然后用补丁直接更新该 HTML 和它自己的资源；不要创建递增版本。只有用户明确要求“另存一版/保留当前版本/重新生成一份”时，才创建新的 `v002/` 等版本，并保证各版本资源独立。
- 新建任务或显式新建版本前检查目标是否存在；若存在，改用新的任务 ID 或版本。禁止对历史任务使用覆盖式重定向、强制复制或其他会静默替换文件的写法。

- 根画布固定为所判定的设备尺寸，并确保浏览器 viewport 与画布一致。
- 新任务按 [references/html-first-auto-layout.md](references/html-first-auto-layout.md) 生成 V2 结构：根画布标记版本，复制布局模板到当前版本资源目录，并用 `f-row / f-column / f-wrap / f-overlay / f-viewport` 表达布局；固定设计稿仍可保留明确宽高，不得用绝对定位模拟普通行列排列。历史页面连续修改时沿用其既有布局版本。
- 使用 CSS 还原布局、比例、层级、间距和响应规则；纯背景不能使用 CSS `background-image`，而必须以根画布内第一个独立 `<img>` 图层呈现。规则矩形/圆角矩形可用独立 CSS 底板还原视觉，但必须标注最终 Rectangle 语义；Capture 后默认重建为原生 Rectangle，只有完整满足前述透明 SVG 根 Frame 例外时才直接验收。此例外不得反向改变本步骤原有的 HTML 表达和视觉实现选择。不规则轮廓和需要路径编辑的装饰使用独立 SVG/形状子层。不要用未标注语义的纯样式 `div`/伪元素承担最终绘制。
- 显式为每个文本层设置 `font-family` 和数值型 `font-weight`；角色默认值仅在视觉证据不足时使用：正文优先 `400`，按钮/控件优先 `500`。避免使用 `font-weight: bold`、浏览器默认的 `<b>`/`<strong>` 粗体、或把标题统一写成 `700`；确需强调时用已验证的具体字重，并可通过颜色、字号或间距表达层级，不能只靠加粗。
- 只声明实际已加载且同时可被浏览器与 Figma 使用的字体字重。若 Web Font 仅提供 `400`/`500`，不得在 CSS 中请求不存在的 `600`/`700`，以免浏览器合成粗体或 Capture 后发生字重替换。
- 为可编辑文字显式使用整数 `px` 的 `font-size`，并统一使用 `line-height: normal`；字号优先使用偶数，`letter-spacing` 默认设为整数 `0px`，文本容器的位置、宽高和内边距也优先使用整数 `px`。不得用小数 `rem/em`、固定/百分比/无单位行高或缩放变换间接得到字号。响应式预览可改变布局，但 Capture 使用的最终标准画布必须落到这些值。
- 不要对根画布、包含文字的祖先节点或文字节点使用 `transform: scale(...)`/非整数 `zoom` 来适配高分辨率参考图。应先将参考图坐标归一到最终画布，再把各文本属性设成最终整数值；否则即使 CSS 声明为整数，Figma 仍可能采集成小数。
- 使用 Hugeicons 图标库。
- 让文本、按钮、卡片、画框、每个前景 SVG/图片与背景保持独立 DOM 元素；不得以单张截图、复合背景或不可编辑 Canvas 替代。
- 对背景、画框、人物、书籍及其他位图直接使用 `<img>` 元素作为其唯一视觉节点；不得建立只包裹这一个 `<img>` 的无职责 DOM 容器。页面 Capture 后，一个 `<img>` 必须对应一个直接图片图层，不得对应“外层 Frame + 内层图片”的两层结构。
- 对按钮、卡片、木牌、平台、砖块、色带、圆点和可由少量路径表达的简单装饰建立显式形状层。DOM 容器负责布局与交互，形状层负责可见外观；规则矩形/圆角矩形标注 `data-figma-node-type="RECTANGLE"` 与 `data-corner-radius`。直线标注 `data-figma-node-type="LINE"`；高视觉权重不规则轮廓使用显式 SVG/path 并标注 `data-figma-node-type="VECTOR"`，不得以伪元素或 CSS `clip-path` 作为其唯一几何。Capture 后按标记批量审计和重建；完整满足前述透明 SVG 根 Frame 例外的节点不重建，CSS 盒模型结果仍不得直接交付。
- 对已判定为完整视觉原子的资源只使用一个 `<img>` 节点，不再用独立 DOM 文字、伪元素或 CSS 图形重建其内部固定内容。不得拆绘完整 IP 的服饰、表情或道具，不得在完整书籍图片上再次叠加书名、作者名或封面图案；若生成资源缺少这些内容，应重新生成/编辑该图片，而不是用 HTML 覆盖缺陷。复杂画框内部的 UI 不属于画框图片，必须用与画框图片同级或在真实内容容器内的独立 DOM 实现。
- 高精度匹配组件的视觉与状态，实施参考图中明确存在或有充分证据的交互，例如按钮反馈、悬停、按下、弹窗/面板显隐和导航状态；纯装饰 IP、画框、礼物和插画默认不添加点击事件或透明热区。交互后仍应保持组件样式与层级正确。
- 在内部源页面中加入 Figma HTML Capture 所需的 capture 脚本：
  `<script src="https://mcp.figma.com/mcp/html-to-design/capture.js" async></script>`
- 上述静态远程脚本只属于内部源 HTML；构建脚本会移除它并在唯一 `*-capture.html` 中改为双通道条件加载器。不要把内部源 HTML 作为预览链接或插件入口交付给用户。

### 4. 本地预览与视觉校验

通过本地 HTTP 静态服务器预览页面（必要时不要直接依赖 `file://`）。预览地址必须包含任务唯一目录和版本路径；打开后核对地址栏、页面标题中的任务/版本标识以及 HTML 绝对路径，确认不是历史文件或可变别名。使用目标尺寸打开并截图，逐项比对整体构图与组件细节：页面完整性、文字大小与字重、组件比例、圆角/描边/阴影/材质、层级关系、交互状态、图片/字体加载和滚动条/裁切。

在该页面仍以目标尺寸加载时运行 `scripts/check_composition.mjs`。脚本通过只能证明 DOM 与契约一致；还必须人工对照参考图确认契约本身没有量错。主体数量、锚点、目标边界、锁定比例或必需属性任一失败时停止 Capture。

执行输出隔离检查：列出本版本 HTML 及其 CSS、JS、图片和字体依赖，确认全部位于当前唯一版本目录或来自明确的只读公共依赖；通过路径和校验值确认旧版本文件没有因本次任务发生变化。只有发现共享可变资源、依赖越出当前版本目录或可变路由时，才分别打开当前和上一版本 URL 做回归检查；依赖闭包稳定的 Inline/External 版本不重复打开旧页面。发现风险时先复制到当前版本的独立资源目录并修正 URL，再继续 Capture。

执行字重专项校验：在浏览器检查 computed style、实际加载字体和字重，确认不存在意外的 synthetic bold，并以现有综合截图在相同显示比例下逐文本块比较笔画厚度和字面面积。正文 `400`、按钮/控件 `500` 仅是证据不足时的默认值；发现某块文字偏细或偏粗时，只对该块比较同字体的相邻可用字重并修正，不新增默认整页截图、不批量改变同角色的其他文字。若无法明确区分相邻字重，选较轻的一档。任何 `600`/`700` 都必须能追溯到用户要求或参考图对照证据，不能仅因浏览器默认样式、元素标签或字体回退而出现。

执行文字排版校验：遍历可编辑文字的声明样式，确认 `line-height: normal`，并检查 `font-size`、`letter-spacing` 以及文本容器几何值是否出现无依据的小数。发现小数时先排查祖先 `transform/zoom`、`rem/em` 和高分辨率比例换算，再用相邻整数候选截图对比；浏览器把 `normal` 计算成像素值属于自动排版结果，不要反写成固定行高。

对每张透明前景执行可见边界校验：将 HTML 截图中的实际可见 alpha 边界与参考图记录的主体边界逐项比较，至少核对 `x/y/可见宽/可见高`。PNG 文件外框、DOM 外框或 Figma 节点外框即使数值相近，也不能代替此检查。人物、IP、画框和大装饰的可见宽高或位置出现明显差异时，必须先按 alpha 边界反算并修正，再进入 Figma Capture。

对每张透明前景执行主体内部 Alpha 完整性校验：在最终显示尺寸的 `100%` 和 `200%` 下，将抠图前文件、alpha 蒙版/透明区域热力图、深色底合成、浅色底合成和 HTML 实际合成并排对照。逐项核对视觉原子内部清单，确认来源中完整的结构没有变成透明缺口；特别检查浅色、高光、发光道具、眼白、牙齿、皮肤边缘、手指、头发和服饰。发现主体内部新增透明岛或背景穿透时，先局部修复 alpha 蒙版并重新完成本项检查，不得进入 Figma Capture。

执行视觉原子完整性校验：逐项对照其内部清单，确认参考图中可见的固有结构和印刷内容均已包含在同一图片内。隐藏完整 IP `<img>` 时，服饰、表情、道具和固有光影必须一起消失；隐藏复杂画框时，框体必须消失但框内卡片、标题、正文和按钮仍应存在；隐藏礼物图片时，属于动态 UI 的促销标签仍应独立存在。对书籍重点检查封面文字/插画、书脊、页芯、后封露边和厚度。若缺项或边界错误，回到图片生成与资源拆分阶段修正。

执行一次资源隔离检查：临时隐藏纯背景以外的每个前景 SVG/图片、画框、卡片和导航，确认其他元素不会随之消失；临时隐藏背景，确认 IP、画框和所有 UI 仍独立存在。检查 DOM：背景必须是根画布第一个子元素的 `<img>`，且根画布没有 `background-image`。若发现任何前景元素来自合成参考图，必须回到“生成视觉资源”重新拆分后再采集。

内部源 HTML 通过开发预览后，立即构建同目录的唯一 `*-capture.html`，按 `officialPayloadRisk` 锁定 Inline 或 External 资产模式后再执行该模式的预检。按 [references/preview-service.md](references/preview-service.md) 依次执行 `status → register → verify`，只有服务身份、任务/版本路由、磁盘 Capture SHA-256 和 HTTP 返回字节一致时，才通过返回的稳定 HTTP URL 在目标尺寸打开该文件，完成正式综合截图、构图检查和字体度量；图片/字体依赖继续复用已有资源清单、审批指纹和浏览器运行时检查，不在服务层建立第二套清单。Inline 模式且环境允许时再以 `file://` 打开同一磁盘文件，确认插件模式的图片、字体、Hugeicons 和画布边界与 HTTP 预览一致。External 模式的插件与官方 Capture 都使用已验证的同一 HTTP URL，并在完成导入前保持本地服务运行。若 `file://` 明确受安全策略阻止，记录环境限制并继续使用已验证的同一 HTTP URL，不创建第二份文件。构建、允许通道的实际页面内容或稳定服务验证失败时只修复对应构建/依赖/服务问题；不得重新生成已经通过视觉检查的资源。

#### HTML 审批门（所有任务）

完成内部源 HTML、唯一双通道 Capture HTML、静态预检、构图报告和最终截图后必须暂停，不得直接进入 Figma。HTML 审批回复必须同时提供：一个明确标为“预览并可用于浏览器插件采集”的稳定 HTTP URL、一张当前版本的最终预览图、目标尺寸和简短验证结论。预览图必须直接使用刚通过正式综合截图与构图检查的 Capture HTML 截图，尺寸等于目标画布，并用标准 Markdown 图片语法展示；本地图片必须使用可渲染的绝对路径。不得以参考图、旧版本截图、局部截图、测试图或文件链接代替这张预览图。仍不并列展示内部源路径、Capture 文件路径、`file://` 路径、构图报告链接、文件卡片或第二个预览入口，除非用户明确索要。审批询问必须作为最终回复末尾的独立醒目引用块，使用 `🟠` 作为可靠的橘色视觉锚点，并将整句加粗；不要依赖可能被客户端过滤的 HTML/CSS 字体颜色。固定格式为：

> 🟠 **HTML 已完成。如果效果可以，请回复“同意”或明确授权导入 Figma；如需修改，请直接描述或标注问题。收到明确审批前不会导入 Figma。**

该格式只增强提示可见性，不改变审批语义，也不能把用户尚未发送的回复视为审批。同时在内部记录当前源 HTML、双通道 Capture HTML 及其全部本地依赖的路径与校验值，作为本次待审批文件指纹；用户审批等待时间不计入实际执行耗时。

有效审批必须在当前审批语境中同时表达“这个 HTML 版本通过”和“授权开始导入 Figma”。`同意`、`确认`、`可以导入 Figma`、`请导入 Figma`、`继续导入`、`开始导入`、`按这个版本导入`、`这个版本通过，可以继续` 等无附带修改要求的表达均可接受；按语义判断，不做脆弱的单关键词匹配。`好`、`行`、`可以`、`继续`、`OK`、`差不多`、`先这样`、`收到` 等没有明确关联“当前版本 + 导入 Figma”的模糊回复不构成审批，应继续等待或简短确认。任何包含“但是/不过/同时请修改”等修改要求的回复都不构成审批，即使其中出现“同意”。用户在任务开始时提出“放到 Figma”、提供 Figma 链接，或此前授权在字体隔离条件下使用插件，只说明最终目标或允许的导入通道，不能代替看到当前 HTML 后针对当前文件指纹给出的审批。

审批只绑定所记录的当前文件指纹。用户提出修改后，直接原地优化内部源 HTML 并重建同名 Capture HTML；修改源文件、Capture 文件或任一本地依赖后，之前的审批立即失效，必须重新运行双模式预检、构图检查和最终截图，再重新请求审批。文件指纹未变化时，Capture 的纯技术失败、同通道重试或 Figma 内部的节点类型/字体绑定/Frame 规范化不需要重复审批；若解决问题必须回到 HTML 或资源层改变视觉内容，则重新进入本审批门。

有效审批到达前，不得新建 Figma 文件、创建 Capture ID、打开插件导入、调用会写入 Figma 的工具或提前建立占位节点。有效审批到达且文件指纹未变化后，继续第 `5` 步。

### 5. 选择首次导入通道并启动采集

先再次核对 HTML 审批对应的文件指纹未变化；没有有效审批或指纹已变化时立即返回第 `4` 步，不得继续。审批有效时再根据“Figma 目标策略”确定目标文件和目标页面节点：有用户链接时解析并使用其中的 `fileKey` 和 `nodeId`；没有链接时创建文件。检查目标节点可访问后，使用字体预检的结果选择且只选择一个首次导入通道。

**官方通道**：确定并记录一个用户级固定的 Figma HTML Capture 专用 Chrome profile 目录。若目录已存在，直接复用；若不存在，则创建空白专用 profile。该目录不得指向、复制自或覆盖用户日常 Chrome 的任何 profile，也不能使用一次性临时目录代替。除非用户明确要求清除，否则不得删除、重置或重建该专用 profile；若 profile 损坏，应先报告并征得用户确认后再处理。先用该 profile 打开不带 Capture hash 的最终稳定 HTTP URL 并完成下段运行时预检；通过后才调用 Figma 官方本地 HTML Capture 工具生成该页面专用的一次性 `captureId` 和 `figmaendpoint`。每次重新采集必须生成新的 Capture ID，不得复用已提交或已完成的 ID。

使用专用 profile 启动新的独立 Google Chrome 实例，打开已经通过审批的唯一 `*-capture.html` 稳定 HTTP URL；不得改回内部源 HTML。启动时除专用 `--user-data-dir` 外，固定加入 `--disable-backgrounding-occluded-windows`、`--disable-renderer-backgrounding`、`--disable-background-timer-throttling` 和 `--disable-features=CalculateNativeWinOcclusion`，避免独立窗口被遮挡后暂停 Capture。先将该窗口置于前台并确认：`document.visibilityState === "visible"`、`document.hidden === false`、`document.fonts.status === "loaded"`、每种目标字体的 `document.fonts.check()` 为 true、所有关键图片 `complete && naturalWidth > 0`、目标尺寸的 `#canvas` 唯一、且一次 `requestAnimationFrame` 能在短时间内实际回调。External 模式还要确认相对图片/字体请求全部返回成功。任一条件未满足时不创建 Capture ID。

运行时预检通过后生成 Capture ID，在同一预览 URL 的 hash 中附加工具返回的采集参数和 URL 编码后的精确根选择器；双通道加载器检测到这些参数后才动态加载官方 `capture.js`。若浏览器已打开相同 base URL，单纯修改 hash 不算加载完成，必须执行一次完整导航或页面 reload，并再次确认 `data-capture-mode="official-http"` 与官方脚本已加载，禁止在旧页面状态上直接轮询：

```text
http://127.0.0.1:<port>/<path>#figmacapture=<captureId>&figmaendpoint=<URL-encoded endpoint>&figmadelay=1000&figmaselector=%23canvas
```

官方通道不要通过 AppleScript、现有浏览器窗口或用户当前标签页执行操作。记录并核对当前地址，确认路径包含本次任务唯一目录与版本、正是最终文件，且 URL 不含资源隔离检查使用的查询参数。禁止把固定 `/index.html` 路由重新指向当前版本。官方通道不检查、不安装和不调用任何 Chrome 扩展；采集由页面内的 Figma 官方 `capture.js` 自动完成。

**本机字体通道**：仅在字体预检命中本机字体隔离条件时使用。先加载并遵守 `chrome:control-chrome` skill，只在用户已有 Chrome 中为当前任务打开一个专用新标签，通过 `file://` 打开已经通过双模式预检的同一 `*-capture.html`；等待图片资源和 `document.fonts.ready` 完成后，调用用户已经安装并授权的 Figma 导入插件，将页面直接导入已确定的目标文件/页面。若浏览器安全策略明确阻止自动导航 `file://`，使用用户审批时看到的同一稳定 `127.0.0.1` 预览 URL 作为插件入口；回退前必须核对服务内容与磁盘 Capture 文件校验值一致，并再次核对标题、任务/版本标识、目标画布尺寸和截图一致性，不得改成别名路由、外部页面、内部源 HTML 或不同内容。不得创建 Capture ID，不得访问或修改其他标签、账号数据和扩展设置，也不得把本机通道扩大为普通页面的默认流程。记录插件返回或新建的目标根节点 ID，后续只处理该子树。用户明确表示将自行使用现有浏览器插件时，仍同时交付当前版本的最终预览图和这一个稳定预览 URL；仅在用户明确要求本地文件时再补充同一 Capture HTML 的绝对路径。

### 6. 完成选定通道的导入

官方通道在 Chrome 打开采集 URL 后，先通过当前采集页确认 `document.visibilityState === "visible"`、`document.hidden === false`、`document.fonts.status === "loaded"`、所有关键图片 `complete` 且 `naturalWidth > 0`，并确认 Figma `capture.js` 已加载；未满足时先修正窗口可见性或资源加载，不开始无意义轮询。等待约 5 秒后，再使用同一个 `fileKey` 和 `captureId` 查询状态：

- `pending`：页面仍在加载或序列化；等待约 5 秒后继续轮询同一个 ID。
- `processing`：数据已提交并正在转换；等待约 5 秒后继续轮询同一个 ID。
- `completed`：记录返回的 Figma 节点链接，进入验证与清理。

若连续 2 次为 `pending` 且服务端没有收到提交迹象，立即重新检查页面可见性、脚本加载、字体和图片状态，不要先机械轮询 10 次。正常情况下最多先轮询 10 次；若仍未完成，核对本地服务、Chrome 地址、capture 脚本、hash 参数和资源加载情况，再继续轮询或按异常处理执行。不得因 `pending` 或 `processing` 改用扩展、Playwright 或新的 Capture ID。Capture ID 已提交后不可再次打开同一个采集 URL；需要重采集时必须创建新 ID。

本机字体通道不轮询 Capture ID。等待插件确认导入完成并记录目标根节点；若插件未返回明确状态，只读取一次目标页面中新建的当前任务节点并用任务名、画布尺寸和创建时间确认，禁止扫描或修改其他历史节点。插件失败时按异常分支报告或重试同一本机通道，不得静默切回已知字体不稳定的官方通道。

### 7. 验证与清理

Capture 后需要修复字体导入绑定或规范化节点类型时，完整读取并执行 [references/figma-normalization.md](references/figma-normalization.md)。

读取最终 Figma 节点 metadata，验证宽高必须等于目标尺寸（Pad 为 `1024 × 640`），并验证根画布的首个/最底层子节点是命名清晰的背景图片节点（例如 `背景/纯场景背景`），不是根 Frame 的 image fill；最终导出图的四边和四角也必须由背景有效像素覆盖。逐项按 `composition-contract.json` 核对主体数量、Figma 节点类型、锚点和目标边界，再对照 HTML 预览和参考图检查背景、文字、图片、按钮、卡片和整体比例；脚本容差沿用契约，不得只比较整个根 Frame。透明前景仍必须按可见主体边界和主体内部 Alpha 完整性验收，不得因 Figma 图片节点外框尺寸正确就判定人物、画框或装饰比例正确，也不得把主体内部的背景穿透误认为高光或真实镂空。逐一读取可编辑文本节点的实际 `fontName.family/style` 和 `lineHeight`，并用字体映射表逐块核对高视觉权重文案的字形类别、字面宽高、换行和基线；“规范化前后截图一致”只能证明规范化没有继续破坏结果，不能证明首次导入字体正确。最终映射包含 `YRDZST` 却得到 `PingFang SC`、替代字体字形，或代表文本的字面宽高/换行与 Capture 前度量指纹明显不符时必须拒绝直接交付；官方通道结果正确时直接保留。若当前 Figma 执行环境能够加载同源字体，先做三阶段指纹和受控 fresh Text 替换；只有 fresh Text 仍不能满足 DOM 字形、换行与度量指纹，或字体无法在该环境安全加载时，才回到字体预检所指向的本机字体通道。此抽查合并进既有字体审计和最终综合截图，不额外创建专用验收页面或截图。只有当前执行环境通过同源/度量门槛的字体，才批量清除临时绑定、写入真实字体并设为 `lineHeight=AUTO`；本机字体通道导入的 Text 或无头环境无法同源加载的字体只做只读审计，保留其已正确解析的 family/style、字形与换行。每种字体族/样式只抽查一个代表节点。确认字体确实不存在时自动换近似字体后再验收。若导入把其他 HTML 整数转换成小数，先修复祖先缩放或单位并重新导入，不把小数结果直接作为最终稿交付。

使用 `use_figma` 读取精确节点类型并完成前景语义审计；不要只依赖 metadata 的标签显示，因为 Group 或某些导入结构可能被摘要为 Frame。至少输出并核对以下结果：

- 背景图片节点恰好位于最底层，且不包含前景。
- 背景、完整 IP、复杂画框、复杂礼物、书籍和其他完整视觉原子图片均为所属画板/真实容器的直接叶子图片图层；其外部包装 Frame/Group 数量为 `0`。带 `IMAGE` fill 但无容器职责的叶子 Frame 数量也必须为 `0`。
- 背景以上的简单视觉元素为 Rectangle、Ellipse 或 Vector；纯视觉组合为 Group。
- 规则矩形和圆角矩形底板默认全部为原生 Rectangle，圆角可在 Figma 属性面板直接编辑；除完整满足前述透明 SVG 根 Frame 例外的节点外，这类底板的 Vector 数量为 `0`。例外节点必须单独列出透明 Frame 与唯一可见子节点，并确认子节点可直接编辑圆角。
- 所有承担 UI 功能的图标必须来自 Icon Library：HTML 中逐个核对 `data-icon-library="Hugeicons"` 与 `data-icon-name`；Figma 中逐个核对最终节点类型为 `Instance`，并核对 `Icon/DesignSystem/<published-name>` + `componentKey` 或 `Icon/Hugeicons/<name>` 主组件来源。页面层级中作为最终 UI 图标的普通 Vector、未标注来源的 UI 图标 SVG、通用 `Icon` 占位名和自绘路径数量必须为 `0`；图标主组件内部的库原始 Vector 不计入（Logo、品牌字标、插画内部固有图案、容器底板等非 UI 图标几何也不计入）。
- 文案保持 Text；按钮、卡片等必要 Frame 的可见底板是独立 Shape，而不是 Frame fill。
- 卡片缩略图/照片槽位的图片节点只含媒体内容；卡片边框、圆角裁切、文字、选中态、勾选/锁定图标和状态遮罩均为可单独隐藏的容器/Shape/Text/Icon Instance。若保留媒体裁切 Frame，必须列明裁切边界和焦点职责，图片外不得再有第二层无职责包装。
- 所有保留的 Frame 都能说明具体容器职责；所有保留的前景图片都能说明其视觉原子边界、内部编辑价值和复杂度依据。完整 IP 可直接以“整体替换、内部无编辑需求”作为保留图片的充分理由，不要求额外证明无法矢量化。
- 所有纯装饰图片默认无点击热区；若保留交互 Frame，必须说明参考页面中的交互证据或用户要求。
- “纯样式 Frame”和“无容器职责的叶子 Frame”数量为 `0`。完整满足前述透明 SVG 根 Frame 例外的导入结构不计入这两个统计，但必须单独计数并逐项通过例外条件；其他结果若不为 `0`，继续修正，不得交付。
- V2 中标为 `row / column / wrap` 的真实流式容器最终必须为 Auto Layout；这类容器的 `layoutMode=NONE` 数量必须为 `0`，Auto Layout 直接子节点越界数量必须为 `0`，标签列表必须启用 Wrap。所有保留的非 Auto Layout Frame 必须列明叠层、裁切、滚动、交互、根画布或图标内部结构职责。

官方 Capture 可能根据浏览器 viewport 额外生成一个大于目标画布的外层 Frame。若内部存在尺寸正确的目标画板，先加载并遵守 `figma-use` skill，再将正确画板提升到目标页面顶层、保留其原始绝对位置并删除仅由本次采集生成的空外框；不得删除用户原有节点。移动含文本的 Frame 前，先读取并加载其字体。字体确实不存在时自动映射到字形类别、字重和度量最接近且不偏粗的可用字体，确认视觉无明显变化后再移动。若字体在用户实际环境中已有可靠可用证据、但无头运行时无法加载，不要移动或重排该 Text；在目标画板尺寸正确、视觉一致的前提下保留最小必要容器并继续规范化其他节点，禁止仅因运行时字体隔离阻断交付或无依据回退到 `700`。

若正确背景资源被采集为根 Frame 的 image fill，优先按规范化顺序把该 fill 提取为根节点第一个/最底层的叶子 Rectangle 图片层并清空根 fill，不因这一语义问题重导。只有实际导入了错误目录、旧版本、重复节点，或采集内容/尺寸本身错误时，才先确认节点 ID、修正 HTML，并按原先选定的通道重新导入；官方通道创建新的 Capture ID，本机字体通道继续使用当前唯一 URL。只保留本次任务最终正确节点，不触碰历史节点。

### 8. 交付

向用户返回：

- HTML 审批阶段必须同时返回一张当前版本的最终预览图，以及一个清晰命名的稳定预览 URL；URL 指向唯一 `*-capture.html`，并注明“该链接也可直接用于浏览器 Figma 插件采集”。预览图使用刚通过最终校验的 Capture HTML 整画布截图，以标准 Markdown 图片语法直接展示。不要再把相同 URL 展开成网站卡片后重复列出，也不要同时发送源 HTML、`file://` 路径或第二个 HTML。
- 本次任务唯一 ID、目标画布尺寸和简短验证结果；新任务只需说明没有覆盖历史任务，同一任务内修改只需说明已原地更新。内部源路径、Capture 文件路径、资源目录、关键 PNG、构图报告和预览截图路径默认不展示，只有用户明确索要排障信息或本地文件时才返回。
- Figma 文件/节点链接。
- 最终画布尺寸和验证结果。
- 简要说明主体数量、锚点、比例和形状不变量均已通过；构图契约与运行时报告路径默认保留在内部。
- 前景资源语义审计结果：Rectangle/Ellipse/Vector/Group/Text 数量、保留 Frame 的职责清单、完整视觉原子图片清单及其判断理由、交互图片清单。
- 若发生重采集或删除错误节点，简要说明处理结果。
- 不输出字体探测、重复核对、无头运行时缺字标记或内部重排测试过程；字体存在时只交付正确字体结果，字体确实不存在并已自动替换时只简短列出最终字体映射。

## 异常处理

仅当异常实际发生时，完整读取 [references/exception-handling.md](references/exception-handling.md)，再执行其中匹配项；稳定预览服务的安装、身份、端口、路由、恢复或卸载异常同时读取 [references/preview-service.md](references/preview-service.md)。正常成功路径不要预加载或逐项检查其他异常分支。异常修复后返回“效率优先执行路径”的最近一个稳定阶段继续，不要从头重跑整套流程。

## 默认配置

- 时间：标准目标 `30 分钟`；轻量 `20–30 分钟`、中等 `30–45 分钟`、复杂 `60–90 分钟`。开始 5 分钟内完成分级，预计超过 30 分钟时主动报告；质量硬门槛优先于时间目标
- HTML 审批：所有任务在完成内部源 HTML、唯一双通道 Capture HTML、构图报告和最终截图后暂停；HTML 审批阶段对用户同时展示一张当前版本的最终预览图和一个明确预览 URL，只有用户明确确认当前版本并授权导入 Figma 才继续。审批提示固定在回复末尾使用独立引用块、`🟠` 橘色视觉锚点和整句粗体，不依赖 HTML/CSS 字体颜色。审批绑定内部源 HTML、Capture HTML 和本地依赖校验值，任一发生变化即失效；模糊回复或附带修改要求不算审批
- 位图清晰度：新生成、重型编辑和可替换源裁切首选 `2×`，最低有效倍率为 `1.5×`；`1.5×–<2×` 记录为“接近 2×”并正常通过 `100%/200%` 检查，低于 `1.5×` 的不可替代源素材才作为需 HTML 明确验收的例外，禁止用插值伪装有效倍率
- 构图：新任务必须建立 `composition-contract.json`，在真实浏览器中检查主体数量、锚点、目标边界、锁定比例、层级和必需属性；参考图与标准画布比例不同时延展/裁切纯背景并重排留白，不拉伸主体或增加主体
- 尺寸判定优先级：用户指定具体尺寸或设备类型/方向（Pad/平板、手机横屏、手机竖屏） > 等比例标准画布 > 最接近的标准宽高比 > 画面形态推断；设备类型/方向明确时按对应标准画布执行，不因参考图比例改判
- Pad：`1024 × 640`
- 横屏手机：`812 × 375`
- 竖屏手机：`375 × 812`
- 图标：Hugeicons
- 字体：先复用同一文案/模板已确认且当前字形未改变的映射，再做手写体证据判定；品牌标题“知识商城”=`Source Han Serif CN Medium`；确认的手写风格中文=`YRDZST Regular`，当前版本目录内 `@font-face` 的 Inline/External 加载与同源/度量验证通过时优先官方 Capture，仅依赖本机安装或同文件同加载条件已有官方失败证据时使用本机字体通道；圆体/圆润黑体属于非手写字体，优先使用两端共同可用的最接近圆体，没有合适圆体就用 `PingFang SC`，不触发 `YRDZST` 检查或阻断；字号大于 `24px` 的纯数字/数字主体=`D-DIN`；其余中文=`PingFang SC`；用户对当前任务的明确指定、纠正或“已安装”说明优先。所有文字默认 HTML `line-height: normal`、Figma `lineHeight=AUTO`、源设计无特殊字距时 `letterSpacing=0`
- 字号：优先偶数整数；仅在参考图对照证明奇数/小数明显更准确时例外并记录原因
- 图片资源：纯背景、完整 IP/人物、复杂画框/礼物、照片/复杂纹理及其他无需编辑内部结构的完整视觉原子使用用户提供的独立原始图片或图片生成工具；生成通道依次为 `image-gen` + `image2`、`image-gen` 的其他可用图片模型、当前环境已有的其他生图/图片编辑模型。首选工具或模型不可用时自动降级并继续，不把可用性缺失计为生成失败，也不因此结束任务；调用前加载 `imagegen` skill，前景图片使用透明 PNG，所有降级通道保持相同的质量与 QA 门槛
- 透明色键：只有直接真实 alpha 不可靠时才使用与主体色域差异最大的单一高饱和纯色。浅绿、白色或发光主体禁止白、灰、绿、青背景，默认使用已有成功记录的纯洋红 `#FF00FF`；其他主体逐项选择不进入其边缘、高光、发光及半透明区域的高对比色键。最终落点背景不参与选色优先级，只用于最终合成 QA。生成色键以 `--generated-key-input` 做固定计划色族自适应提取；允许同色族渐变、亮暗变化和统一色漂移，主体有意贴边时用 `--allow-subject-touch-edge` 声明。多色/不兼容边界、手动放宽参数、未声明的主体触边、可见键色残边或主体损伤仍拒绝。选色复用既有资源分析，不生成多张候选、不新增图片生成门槛，最终仍须通过实际页面、深色和浅色背景的边缘与内部 Alpha `100%`/`200%` 检查
- 资源路由：新任务必须建立 `resource-manifest.json` schema v3，先通过生成前资源计划预检，再与 `composition-contract.json` 和 HTML `data-resource-id` 一起通过 Capture 前预检；图片路由失败只能切换图片取得方法，不得降级为 SVG/CSS。只有用户明确要求内部编辑或存在可靠分层矢量源文件时允许记录例外
- 矢量资源：UI 图标以发布组件或 Hugeicons 主组件的 Instance 交付，Vector 只作为主组件内部几何；简单几何、动态 UI 和确有内部编辑价值的简单装饰使用 Rectangle/Ellipse/Vector/Text/Group；扁平风格不自动等于 SVG
- 图层策略：所有图片直接作为叶子图片图层，图片外不套无职责 Frame/Group；背景以上的资源必须独立，但根据视觉原子边界选择图片或矢量
- Frame 策略：V2 新任务中单轴/换行布局默认使用 Auto Layout，真实叠层、裁切、滚动、响应式边界、交互、根画布和图标内部结构可保留普通 Frame；历史页面不自动迁移；纯样式 Frame 验收数量必须为 `0`，完整满足严格条件的透明 SVG 根 Frame 作为导入器结构例外单独审计，不改变 HTML 生成策略
- 交互策略：纯装饰 IP、画框、礼物和插画默认不可点击；仅在参考页面有明确证据或用户明确要求时增加独立交互命中容器
- Chrome：官方通道使用长期保留、与日常数据隔离的 Figma HTML Capture 专用 profile；本机字体隔离分支仅在已有 Chrome 的专用新标签中运行已授权插件
- 默认采集：字体预检通过时使用 Figma 官方 `capture.js` + 一次性 Capture ID + 约 5 秒间隔轮询至 `completed`；本机字体隔离时直接使用已授权的本机 Chrome/Figma 导入路径，不先创建 Capture ID
- 首次安装：仅在用户明确执行独立环境初始化时检查并准备 Codex/Figma/Chrome/Computer Use 相关能力；安全的 Skill 私有依赖可自动修复，持久授权使用真实授权按钮，其他人工步骤提供官方链接或精确设置路径。普通图片任务不读取初始化状态、不运行全局环境检查
- 稳定预览：默认地址 `127.0.0.1:41972`，状态和路由保存在 Skill 目录外；常驻安装需要一次明确授权，日常任务只执行身份检查、当前任务/版本注册和磁盘/HTTP 字节验证。未知端口进程、服务不可恢复或身份不匹配时阻断稳定链接交付，不静默换端口或退回临时链接；服务在线不代表获得 Figma 写入授权
- Chrome 扩展：由独立首次安装流程提供 Figma 官方扩展入口与 ChatGPT 浏览器连接路径；不代替用户完成持久授权且不影响官方自动导入。实际导入中普通页面默认不使用扩展，仅在用户明确要求、确认备用方案或命中本机字体隔离条件时使用既有扩展
- HTML 交付：内部保留可维护源文件，对外只生成一个 `*-capture.html`；`officialPayloadRisk=false` 时资源全部内嵌，风险为 true 时仅图片/字体以当前版本目录相对 URL 无损加载，Hugeicons 始终保留库溯源，页面边界严格等于目标画布。普通预览和插件模式不加载远程 Capture 脚本，只有带官方 hash 参数的 HTTP(S) 模式才动态加载。Inline 文件通过 `preflight_html.py --offline` 与 HTTP 模式预检；External 文件通过 HTTP 模式和依赖/哈希闭包检查。交付时同时提供指向它的一个稳定预览 URL，以及刚通过最终校验的整画布预览图
- Figma 目标文件：优先使用用户提供的链接；未提供时先读取当前账号的 plan。账号对“猿辅导体验设计”plan（`team::1634053011581078191`）具备写权限时优先使用其 Drafts；否则自动使用当前账号自己的默认/个人可写 plan 与 Drafts，不尝试你方团队、不传 `projectId`，也不在外部账号的用户可见信息中展示团队 plan 名称或 ID。
